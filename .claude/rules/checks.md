# The checks and the workflows

What each check does and how CI runs it. The commands, and when each check is due, are in `CLAUDE.md`; `CONTRIBUTING.md` is the contributor's account of the same workflows.

## Workflows

- `.github\workflows\pipeline.yml` runs on pull requests and pushes to `main` on a Windows runner and is required by branch protection; a pull request the owner did not open also needs the owner's approval, through `.github\CODEOWNERS` and the "Owner approves main" ruleset, which the owner bypasses for their own.
- It builds Release with the runner image's SDK (no `setup-dotnet`; `global.json` chooses it), tests, checks whitespace only (`dotnet format whitespace --folder --exclude openspec`, because the build already fails on style and analyser warnings; folder mode loads no MSBuild workspace and skips the SDK's generated files, and `openspec`'s archive holds sample `.cs` files outside the solution), publishes the self-contained winget build (`Properties\PublishProfiles\win-x64.pubxml`), zips exactly its five files with `.github\scripts\Compress-WingetBuild.ps1` (which fails on a missing file or any other, a PDB above all, or on a `libonigwrap.dll` of the other architecture) and uploads the zip. The `check` job is a matrix: the `win-x64` leg on `windows-latest` (named `check`, the name branch protection requires) also runs the tests, the Pester script tests under `test\Scripts` and the whitespace check; the `win-arm64` leg, named `check (win-arm64)`, runs on the hosted `windows-11-arm` runner and builds, publishes and smoke-checks only, because an Arm zip cannot be run on x64 (the owner may add it to the required checks). Each leg uploads `cader-<version>-<rid>`. The NuGet global packages folder is cached with `actions/cache`, keyed on every `*.csproj`, `Directory.Build.props`, `nuget.config` and `global.json`; caches are scoped by ref, so only runs on `main` write the cache a release restores from. Measured on 2 November 2026 (PR #204, windows-latest, SDK 10.0.403): the `check` job took 169 s against about 3.5 minutes before. A cache hit is about 81 MB, restored in 10 s, and takes the build from 76 s to 52 s. Folder-mode format takes 10 s against 16 s, and `--no-build` saves about 3 s off the smoke check. The `DOTNET_` first-run variables left the pause before restore at 9 to 10 s, against 14 to 32 s in earlier runs, which is within the runners' own variation, so they are kept because they cost nothing rather than for speed. A pull request touching only `openspec\` or `.md` files outside `.github\` skips all of that after the version check, through `.github\scripts\Test-DocumentationOnly.ps1`; pushes to `main` run everything, and a new commit cancels a pull request's older run.
- Every action is pinned to the commit of its release with the version in a comment (Dependabot keeps the pins current, grouping the `github/codeql-action` steps into one pull request because CodeQL fails when `init` and `analyze` differ, seen 13 November 2026 on 4.39.1 and 4.39.3, and NuGet version updates into one `nuget` group a week; the repository setting requiring pins is turned on once every workflow on `main` has them).
- `.github\workflows\mutation.yml` mutation-tests Core on a runner after each release and weekly, never on a pull request; see Mutation testing below.
- `.github\workflows\codeql.yml` runs CodeQL over the C# (build mode none) and the workflows on pull requests, pushes to `main` and weekly, never as a required check.
- `pipeline.yml` also publishes a GitHub Release tagged `v<version>` when a push to `main` changes `Version` in the csproj (a separate `release.yml` did until 3 November 2026, building and testing the same commit a second time; the workflow was `check.yml` until then too, and its job is still named `check` because branch protection requires that name): the `check` job's "Decide the release version" step compares the csproj with the first parent, so that run names the zip for the plain `Version` instead of `-ci.N`, smoke-tests that very zip and uploads it as the `release-<rid>` artefact after the smoke check (both legs; the x64 leg adds the notes), and a `release` job (`needs: check`, so both legs, no checkout) holds `contents: write`, `id-token: write` and `attestations: write` to download them, find exactly one zip per architecture, attach a build provenance attestation to each and run `gh release create` with both; a commit whose check failed is never released. Nothing reaches winget automatically: `.github\workflows\publish.yml` (`workflow_dispatch` with a `tag` input, one `winget` job in the `winget` environment, which waits for the owner's approval, accepts only `main` and holds the `WINGET_PKGS_TOKEN` environment secret; `contents: read`, `attestations: read`) refuses a tag with a prerelease label, downloads the release's two zips (failing naming the architecture when either is missing), runs `gh attestation verify` on each with `--signer-workflow` `pipeline.yml` and `--source-ref refs/heads/main`, fails when winget-pkgs has no `manifests/s/Source191/Cader` (HTTP 404 from the contents API; the first version is submitted by hand, MAINTAINING.md), then runs a pinned, hash-checked `wingetcreate update --urls "<x64 zip>|x64" "<arm64 zip>|arm64" --submit`, failing loudly without the token. For a stable version the `check` job also writes its `CHANGELOG.md` section (`Write-ReleaseNotes.ps1`) into the artefact, and the release job passes it with `--notes-file` beside `--generate-notes` and `--notes-start-tag` the previous stable tag (`gh release list --exclude-pre-releases`), which `gh release create --help` (gh 2.103.3, 1 November 2026) says prepends it to the generated notes. Immutable releases are off for the repository (`gh api repos/Source191/cader/immutable-releases` answered `enabled: false` on 1 November 2026); a fix is a new version all the same. The first step of `check` (`.github\scripts\Assert-VersionBumped.ps1`) fails a pull request that changes the packaged tool without raising `Version`, so each merge of one is a release. The next (`Assert-ChangelogUpdated.ps1`, sharing `ToolPaths.ps1` with it) fails one that leaves `CHANGELOG.md` unchanged or raises `Version` to a stable version without that version's section and an empty Unreleased; the Dependabot bump step (run by `DEPENDABOT_BUMP_TOKEN`, a Dependabot secret; it fails naming the secret when missing) runs `Step-Version.ps1 -Preview`, so a stable `Version` becomes a preview of the next patch, adds its pull request's Internal line with `Add-InternalChangelogEntry.ps1`, pushes with `[dependabot skip]` in the message so Dependabot keeps rebasing, and a following step removes the `dependabot-branch` checkout so the whitespace check and the NuGet cache key never read it (the four test-only Dependabot pull requests #228, #233, #236 and #237 failed on 13 November 2026 when it did).

## Mutation testing

- Stryker from `test\Source191.Cader.Core.Tests`, as `dotnet stryker`, with the tool pinned in `.config\dotnet-tools.json` (`dotnet tool restore`; 5.0.0, the newest release at least two weeks old on 13 November 2026, where `dotnet stryker --version` is not the tool's version but a dashboard option, so read it with `dotnet tool list`) and the settings in `test\Source191.Cader.Core.Tests\stryker-config.json`: `--test-runner mtp` (xunit.v3 scores 0 % under the VSTest bridge), the project, the `html`, `markdown`, `json` and `progress` reporters and the thresholds. Scope a hand run with `--mutate "**/Domain/*.cs"` style globs, never solution-relative paths. The config file takes no `skip-version-check`; pass `--skip-version-check` on the command line. Reports are under `StrykerOutput\<timestamp>\reports`.
- Measured on 13 November 2026 (Stryker 5.0.0, SDK 10.0.404, a Windows 11 developer machine unless a runner is named): Core has 3,819 mutants, of which 2,858 are tested after the compile-error and ignored ones; 2,342 tests. A full run took 11 min 10 s (score 86.78 %: 2,498 killed, 3 timed out, 357 survived, 24 without coverage) and 8 min 39 s on a second run from a fresh clone (86.95 %), so the same code differs by about 0.2 points between runs. Its markdown report is 95 KB (the job summary's limit is 1 MiB) and its JSON 12 MB, which `Write-MutationRun.ps1` cuts to about 450 KB for the artefact. The fixed part of any run is about 2.5 min (build, then per-test coverage capture), and `--since` is checked only after it, so a mistyped committish costs that too.
- On a `windows-latest` runner (a full run of this branch, run 43478448861): 15 min 27 s for Mutate and 16 min 12 s for the job, 2,858 tested, 2,626 killed, 3 timed out, 229 survived, score 91.22 %, so the runner scores 4.4 points higher than the developer machine on the same code (why is not known; one sample). The job summary took the 95 KB report, and `stryker-output` was 7.2 MB and `mutation-results` 32 KB.
- `--since` runs, from a fresh clone at `db89b8aa`: 6 min 6 s, 6 min 23 s and 7 min 33 s for the ranges starting at `05eaac97~1` (110 Core files changed), `be8f58c5~1` (131) and `ca3bc2ee~1` (125), each testing 2,760 to 2,784 of the 2,858 mutants, because a changed test counts every mutant it covers as changed (the shared fixtures and architecture tests cover nearly everything). Those ranges are sweeping renames; no range between two release tags exists since the rename to Cader (`v0.21.0-preview.1` to `v0.21.0` changed only the csproj, and a run with nothing to mutate took 2 min 33 s). So a release that touches tests costs 6 to 8 minutes and one that changes no Core code about 3, against the 30 minutes that decide the per-release trigger. Scores of `--since` runs (88.6, 92.0 and 88.8 %) cover only the mutants tested and are not comparable with the whole score.
- Three Stryker facts found measuring: `--since` takes a sha or a ref name, not `<sha>~1`; in a linked git worktree it resolves the main checkout's paths, matches no changed file and tests nothing, so measure in an ordinary clone (CI is one); and a changed non-C# file in the test project (this `stryker-config.json` included) makes it test every mutant.
- `.github\workflows\mutation.yml` runs Core's mutation tests on a Windows runner, never on a pull request and never on the path of a merge or a release: after `pipeline` finishes on `main` for a push (`workflow_run`, so a release made with the workflow's token, which raises no `release` event, is still seen), only when the commit carries a `v*` tag (otherwise a notice and stop); every Sunday at 03:00 UTC; and by `workflow_dispatch` (usable only once the file is on `main`). One `mutation` concurrency group without cancel-in-progress runs one job and queues one. The job holds `contents: read` and `actions: read` and no secret; it restores `pipeline`'s NuGet cache read-only, runs `dotnet tool restore` and `dotnet stryker`, appends `mutation-report.md` to the job summary and uploads `stryker-output` and the small `mutation-results` (`run.json` and the cut report) for 30 days.
- The range (`Resolve-MutationRange.ps1`): after a release, `--since` the head commit of the newest finished mutation run on `main` (success or failure; a `workflow_run` counts only if its own commit carries a `v*` tag, since one that stopped at the notice mutated nothing; a schedule or dispatch run always counts) that is an ancestor of the release, so a run replaced in the queue never loses its changes; failing that, the previous `v*` tag; failing that, all of Core. A schedule or dispatch run has no range.
- A finding (`Write-MutationRun.ps1`): after a release, any `Survived` or `NoCoverage` mutant in the changed code; after a full run, a whole score more than 0.5 points below the previous full run's, read from that run's `mutation-results` artefact (skipped with a notice when it has expired, the run then being the baseline). A job of its own, `report`, which holds only `issues: write` and runs nothing from the repository, posts the comment the mutation job wrote (`Format-MutationComment.ps1`: the release, range and run link and at most 50 mutants, or both scores and the five files that fell most; cut to 60,000 characters) on the open issue labelled `mutation`, or opens one assigned to `vars.MUTATION_WATCHER`. The issue stays open until the owner closes it.
- Before publishing: `publish.yml`'s `mutation-notice` job (no environment, `contents: read` and `issues: read`, no secret) runs before the owner's approval, lists the open issues labelled `mutation` with `gh` and prints a `::warning::` and a job summary section naming them (`Get-MutationWarning.ps1`); it never fails or blocks, and `test\Scripts\Get-MutationWarning.Tests.ps1` holds the script and the job's rights.
- The break score is in `stryker-config.json`: 86, decided by the owner on 14 November 2026 from the 91.22 % score of the first run on a runner (less five points, rounded down); the same code scored 86.78 % on the developer machine, so a local run can end below it where the runner does not. It applies to the weekly full run only: a release run passes `--break-at 0` (its score covers just the mutants tested), so it reports its survivors on the `mutation` issue and never fails on score. A failed full run is the alert, through GitHub's failed-run notice; nothing blocks a merge or a release. The scripts' fixtures are in `.github\scripts\fixtures\mutation` (a real report cut to the fields the scripts read, and a copy with the survivors killed). Stryker refuses a config whose `low` threshold is below `break`, so the thresholds are `high` 95, `low` 90 and `break` 86. `test\Scripts\Mutation.Tests.ps1` (Pester, run by `pipeline`) covers the three scripts on the fixtures and holds the `--break-at 0` fact by reading `mutation.yml`. Checked locally on 14 November 2026: a score of 84 % under the config ends with exit 2 ("lower than the configured break threshold"), and `--break-at 0` on the command line overrides it and exits 0.

## Hand-off check

- `dotnet run --project tools\HeadlessTerminal -- check` runs `cader here` with a throwaway name and no prompt, which makes no model call, waits through `StepRunner` for Claude's `Claude Code v` banner, about 12 s, sends Ctrl+Z and waits for `here` to exit, then stops and removes the job by name; exit 1 means `here` did not exit after the detach, 2 that the check could not start (no Release exe, for one), 3 that the banner never appeared (checked 31 October 2026, CLI 2.1.316). Its defaults are relative to the current folder, so run it from `tools\HeadlessTerminal` (CI: `dotnet run --project . -- check` there) after `dotnet build src\Source191.Cader -c Release`.
- It is the one automated test of a real `claude attach` and detach; the console itself never hands over, so the blocked-UI-thread failure it was first built for can no longer happen.
- A [pseudo-console](https://learn.microsoft.com/windows/console/creating-a-pseudoconsole-session) child is started with [`STARTF_USESTDHANDLES`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow) and no handles, or its standard output (and Claude's whole screen) would go to the driver's own stdout whenever that is piped, as in CI.
- The `handoff` job in `pipeline.yml` runs the same check on the runner when the `CLAUDE_CODE_OAUTH_TOKEN` secret exists, and never blocks a merge.
- The same tool has `drive` (scripted keystrokes into a ConPTY pseudo-console, capture to drive-raw.txt), `grid` (replay a capture as a screen) and `count` (plain-text markers). Keys sent before Terminal.Gui has initialised (about 8 s on a cold start) are lost, so scripts start at 8000 ms. Setting `LOCALAPPDATA` does not move Cader's state folder: `Environment.GetFolderPath(LocalApplicationData)` asks Windows for the known folder and ignores the variable (checked 1 November 2026, .NET 10, Windows 11 26100), so a `drive` of a local cader.exe reads and writes the real `%LOCALAPPDATA%\Cader` and the Windows Terminal fragments folder, and is for the owner to run, never an unattended session.

## Smoke check of the packed tool

- `smoke <exe> <worktree-folder>` opens and cancels the Keys help, the wizard, the problem report, the first repository root's dialog on the Config tab and its folder picker (F3), the Open folder with dialog (found by filtering for `with`) with Custom chosen and its file picker (F3), the worktrees view, its help, force remove, the fixed-folder wizard (`n`) and the solution chooser (`s`) on an idle linked worktree holding two solutions, then quits; exit 0 passes, 1 is a blocked UI thread, 2 no exe, 4 a step whose marker never appeared (named in the output).
- `smoke-update <exe>` (U opens What's new, Esc closes it) and `smoke-whats-new <exe>` (What's new opens before the console, Esc, the sessions view) need a stable build that has recorded a newer release or an older `last-run.json`, which CI's `-ci.N` prerelease never is, so they are the owner's, with seeded state in the real `%LOCALAPPDATA%\Cader`; running `smoke-update` after `smoke-whats-new` also shows that a second start opens nothing first.
- Its steps take their keys (by hint) and markers (dialog tab titles, a column only each view has, and the worktrees title's ", selected: " as the scan-finished signal, since the WORKTREE cell reads `repository › slug` and never the folder name) from `Wording`, so a new dialog is one step in `SmokeScript`.
- The `check` job installs the Claude Code CLI (signed out: `claude agents --json` prints `[]`), seeds `~\source\repos\Northwind.Smoke` with the linked worktree `Northwind.Smoke-smoke`, extracts the winget zip into a temporary folder and runs its `cader.exe`, so it is the one test of the bits users install.

## Claude Code contract tests

- They start real sessions, so they carry the trait `Category=ClaudeContract` and skip unless `CADER_CLAUDE_CONTRACT=1`: run them with `$env:CADER_CLAUDE_CONTRACT = 1; dotnet test --project test\Source191.Cader.Infrastructure.Tests -c Debug -- --filter-trait "Category=ClaudeContract"` from a trusted repository. Accepting a help snapshot is copying its `<name>.received.txt` over it, in a change that re-checks the CLI facts in `claude-code.md`. Never add `--bg --resume --help` to them: it starts a session.

- `test\...\Infrastructure.Tests\Contract` drives the solution's own Claude adapters against the installed CLI (version, a `--bg -n` start with no prompt, the listing's fields and state, stop and rm) and compares the commands and options of `claude --help` and `claude agents --help` with `Contract\Snapshots`.
- `.github\workflows\claude-contract.yml` runs them nightly against the latest CLI, with the hand-off check, in a job with `contents: read`; when the install or a contract test fails, a `report` job (`needs: contract`, `issues: write`) reads the outcomes and the `contract-results` artefact and comments on the open `claude-cli` issue or opens one assigned to the `CLAUDE_CLI_WATCHER` repository variable.
- A snapshot difference leaves `<name>.received.txt` in the output folder (and the run's `contract-results` artefact).
- Automated runs, measured: a prompt-less `claude -p` with its standard input redirected and never written waits 3 s for input, fails on it without a model call and exits 1; on a clean machine (a fresh `CLAUDE_CONFIG_DIR`, as on the runner) it registers as an automated run at about 7 s and exits at about 8.5 s, before a listing can see it, and a user's own hooks lengthen that (the owner's SessionEnd hook adds about 10 s; measured 2026-10-31, CLI 2.1.316). The `ClaudeContract` fact checks the automated-run rule by holding the run open with a SessionEnd hook passed through `--settings` that sleeps for 20 s (listed at about 6 s, exit 1 at about 27 s on a clean machine; a user's SessionEnd hooks run as well and add their time). Start such a run after the console is up when checking the screen, since its first listing takes about 10 s.
