# Claude Code CLI facts (verified 2026-10-29, CLI 2.1.310)

Re-verify these, and move the date and version above, whenever a change accepts new help snapshots or raises `ClaudeCodeSupport.Minimum` (the settings row's below-minimum warning, stated as "2.1.309 or later" in the README and `openspec\config.yaml`, which `DocumentedMinimumShould` keeps in step).

- `claude --version` prints `2.1.310 (Claude Code)`; `IClaudeCli.VersionAsync` takes the leading dotted number (`NotRead` on failure) once per run for the settings row.
- `claude agents --json [--all]` is the scripting surface. Fields: pid, id, cwd, kind (interactive or background), startedAt, sessionId, name, status (busy, idle, waiting), state (working, blocked, done, failed, stopped), waitingFor. The job `id` is the first 8 characters of `sessionId`. A stopped session is a row without pid or status.
- An interactive listing row with a pid and no `status` is an automated run (`Domain\AutomatedRun`, sorted out in `ClaudeAgentsListing`), never a session row: the Agent SDK (`sdk-py`, `sdk-ts`; the security-guidance plugin's background review, run after a commit or push and when a turn ends, is one, about 20 s and a few thousand tokens) and `claude -p` (with a derived name such as `tmp-9d`) are listed that way for their whole lives, while a `claude` started in a terminal registers without a status and has `idle` about 130 ms later (measured 2026-10-30, CLI 2.1.314, through the headless terminal). `claude logs <id>` never registers. Their count and memory end the Sessions counts (`◇ 1 automated 216 MB`). How long a `claude -p` stays listed, and how the contract fact holds one open, are in `checks.md`.
- The CLI names a session started without `-n` after its folder (`repos-93`, captured 2026-10-23 on 2.1.309; `Northwind-9d` for `claude -p`, captured 2026-10-30 on 2.1.314), so a session row with no name has not been seen; only the SDK's automated runs, which are never rows, lack one. `ListedName.Unnamed` is a shape the JSON allows (`ClaudeAgentsListing` makes it of a missing or blank `name`), shown blank through `Wording.Name`, and resumed with no `-n`.
- `claude --bg -n <name> [prompt]` starts a supervised session; with no prompt it waits at its own prompt. `attach` accepts a name, `stop` and `rm` need the id. Attaching to a session with no messages lands at that session's own prompt, and Ctrl+Z detaches from it as from any conversation. The CLI has no end-of-options marker: `claude attach -- --help` answers `unknown option '--'` (checked 2026-10-29), so a prompt that starts with `-` would be read as options and Cader refuses it instead. The npm package now installs the same native binary as the installer; Cader never runs a `claude.cmd`.
- A session's transcript `~\.claude\projects\<cwd-encoded>\<sessionId>.jsonl` is written on the first message. Resuming a session with no transcript fails with "source session not found", so adopt (`b`), rename (`r`), open-in-tab (Enter) and resume all check `ITranscripts` first. A transcript file is not proof of messages: `/bg` in an interactive session (seen 2026-11-16, CLI 2.1.325) starts a background job under a new session id, writes a `continued-in` line naming it into the interactive session's transcript, and gives the new id a transcript of only an `ai-title` and an `agent-name` line until its next turn. `claude rm` then `claude --bg --resume <new id>` fails with "source session <id> not found" (the job is listed as failed some 15 s after the resume returned), while resuming the interactive session's id continues the conversation. So `ClaudeTranscripts` counts messages only from a line whose top-level `type` is `user` or `assistant`, and reads nothing else but the first `session-owner` line's `organizationUuid` (Accounts, below).
- `claude --bg --resume <sessionId> -n <name>` continues a *non-background* transcript under the supervisor with the same id (how `b` adopts a terminal session after ending its process). For a *listed background* job the same command with flags starts a copy, as [the docs](https://code.claude.com/docs/en/agent-view) say ("keeps its own saved options"); `claude rm <id>` first (the transcript stays on disc) and the resume then continues the same id under the new name, which is how `r` renames. A listed stopped or failed job is copied the same way (verified 2026-11-01, CLI 2.1.316: the old row stayed listed as failed beside the new jobs), so `R` removes each job first too, like `r`; a job just started or resumed is listed with a pid and no status for a moment, which the console shows as starting (on 2026-11-02, CLI 2.1.316, a runner's first listing of a new job had neither pid nor status for a moment, so the contract fact polls until the row has every field). Never run `claude --bg --resume --help`: it starts a session.
- Interactive sessions register in `~\.claude\sessions\<pid>.json`; they cannot be attached, stopped or removed from outside. Windows Terminal closes a tab when its root shell exits with code 0 and keeps it after a kill, so `d` and `C` end claude and then end the tab's shell cleanly (`TerminalTab`, `IProcessRegistry.EndCleanly`).
- **The `sessions` and `jobs` folders (seen 18 November 2026, CLI 2.1.327, with `FileSystemWatcher` in PowerShell 7):** `<Claude folder>\sessions\<pid>.json` is one file per running session, background ones included, holding `status` and `statusUpdatedAt`, rewritten when the status changes; beside it are `<pid>.<hash>.key` files, written when a session starts. `<Claude folder>\jobs\<id>\state.json` is one per background job, holding `state`, written as `state.json.tmp.<hex>` and then renamed over `state.json`, so a watcher sees Created and Changed on the temporary name and Deleted and Renamed on `state.json`; a job's `timeline.jsonl` is written beside it. With the machine quiet a job wrote once in 40 seconds, and a `claude agents --json` listing (2.3 s) wrote nothing for any job but the one running it. Both formats are undocumented and internal, so Cader never opens these files: `Application\ChangeFilter` takes a changed name only as a hint to run the documented listing (`Infrastructure\Files\FolderChanges`, `Application\ChangeWatches`), and the timers stay as the safety net if Claude Code stops writing them.
- Workspace trust is per repository (linked worktrees inherit it), granted only interactively; `claude --bg` in an untrusted folder exits with "Workspace not trusted". Never script edits to the trust records on a developer machine; the exceptions are the CI `handoff` job and the `claude-contract.yml` workflow, which seed `projects.<path>.hasTrustDialogAccepted` in the throwaway runner's own `~\.claude.json` (keys are forward-slash paths with a capital drive letter, e.g. `D:/a/cader/cader`).
- Background sessions do not commit or push on their own (bgIsolation none, sibling worktrees). permission_prompt and idle_prompt notifications fire unattended; agent_needs_input and agent_completed fire only while the native agent view is open, which is why Cader rings its own bell for background rows.
- `"preferredNotifChannel": "terminal_bell"` in settings.json ([terminal configuration](https://code.claude.com/docs/en/terminal-config)) makes Claude ring the terminal bell when it finishes a task or pauses for a permission prompt while the user appears away, which flags the tab showing a session. Claude Code writes `settings.json` with bare LF; anything that rewrites it must keep that.
- **Tab titles (seen 16 November 2026, CLI 2.1.325, Windows Terminal 1.25.3131.0, read through UI Automation):** while a session works, its attach tab's title is a spinning glyph, a space and the session's name (`◐ c-finish-proposals`, then `◑ c-finish-proposals`); an idle session's tab shows the name alone; Claude Code's own tabs show `✳ <topic>` or a spinner glyph and the topic. The glyph reaches a tab Cader opened with `--suppressApplicationTitle`, by a route not yet known (`windows.md`), so Enter finds a session's tab through `Domain\TabTitle.Shows`, which accepts the name alone or after exactly one glyph and a space.
- **What turns the glyph off (checked 17 November 2026, CLI 2.1.326, Windows Terminal 1.25.3131.0, a scratch linked worktree under `%TEMP%`, throwaway sessions given a 1,500-word essay to write; the capture is `claude attach` in the headless terminal's pseudo-console, 30 s, every OSC sequence counted):** the control writes `OSC 0;◐ <name>` 15 times and `OSC 0;◑ <name>` 16 (and queries `OSC 7501;?` once). [`CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1`](https://code.claude.com/docs/en/env-vars) on the `claude attach` alone left 29 glyph titles (it only dropped the `OSC 7501` query), on `claude --bg` alone left 29, and on both left 28, because **a background session's environment is its supervisor's, never the `claude --bg` client's**: a session asked to print `SPIKE_PROBE`, `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` and `TERM_PROGRAM` from a client that had set all three read each as unset. What reaches the session is `claude --bg --settings '{"env":{"CLAUDE_CODE_DISABLE_TERMINAL_TITLE":"1"}}'` (no glyph title in the capture, only the attach client's one `OSC 0` of the executable's path and the `OSC 7501` query), also with `--bg --resume <session id> --settings ...` after `claude rm` (the session wrote its essay and no glyph title either). A hand-run in a real Windows Terminal tab opened with Cader's `wt` arguments never showed the glyph in the control (the name read plain for the 57 s the session worked, with the workstation apparently locked: a lock-screen picture in a screenshot and `LogonUI` running), so the capture is the evidence and the owner's manual check of the real tab is still due. So `ClaudeCli` adds that `--settings` pair to every start and resume; `Variables` on the request, and a line in the attach script, would not reach the session.
- **Accounts (checked 18 November 2026, CLI 2.1.327, field names only, no values printed):** `claude auth status --json` (documented as `--json`, the default; about 1.2 s) answers `loggedIn`, `authMethod`, `apiProvider`, `email`, `orgId`, `orgName`, `subscriptionType`, `planTier`, `configDirectory`, `projectsDirectory`, `loginExpiresAt` and a few flags; it gives no account id. From CLI 2.1.325 on a transcript carries `{"type":"session-owner","accountUuid":…,"organizationUuid":…,"sessionId":…}`, usually as its fourth to seventh line and repeated through the file; of 200 recent transcripts 75 had it, none named two owners, and the latest first owner line was line 1,506. `ClaudeTranscripts.OwnerOf` reads only the first such line's `organizationUuid`, and `AccountCatalogue` matches it to `orgId`, so two seats in one organisation share a label. A `--bg` session started with no prompt wrote no transcript at all in its first eight seconds (so no owner line; checked the same day), which is why the contract fact `ReadTheLoginFromAuthStatus` checks `auth status` alone: reading an owner line would need a model call. `auth status --json` exits 0 only when `loggedIn` is true and 1 when it is false, printing the JSON either way (checked 18 November 2026, CLI 2.1.327, a scratch `CLAUDE_CONFIG_DIR`); with an unverified `CLAUDE_CODE_OAUTH_TOKEN` set it answers `loggedIn: true` and `authMethod: oauth_token`, no `email` or `orgId`, and exits 0. Cader's children never see that variable (`InheritedEnvironment` drops every `CLAUDE_CODE_*`), so on the contract runner, which signs in only through it, the fact reads the logged-out answer (issue #338: the fact expected exit 0 and failed).
- On detach Claude leaves focus reporting on and the cursor hidden and sends a late terminal-version query; `ConsoleRecovery` resets these after every child (only `cader here` runs one now).
- `CLAUDE_CONFIG_DIR` (checked 2026-11-14, CLI 2.1.325, scratch folders under `%TEMP%`, `claude --version` and `claude agents --json`, no login): a full path is used as given and a trailing `\` makes no difference; a folder that does not exist is created (with `.claude.json`, `backups` and `daemon`); a relative value is read against the CLI's own working directory (it created `<cwd>\rel-config`); `~` is NOT expanded (`~\x` created a folder literally named `~` under the working directory). So Cader treats a value as usable only when it is a full path; `~` and relative values are not usable, because no one folder holds every session's files.
