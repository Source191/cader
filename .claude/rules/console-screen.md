# The console screen

How the console is laid out and refreshed. The rules every view follows (reducers, effects and their markers, keys and columns as data in `Wording`) are in `CLAUDE.md`.

## Layout

- The console is one Terminal.Gui application, `Tui\ConsoleScreen`: one settings row (`Wording.SettingsRow`, orange labels and white values as `TextPart`s, an available update in amber; the roots and the worktree root are on the Config tab) to the right of `Tui\LogoIcon` where the terminal draws images, a `Tabs` strip with the fixed titles Sessions, Worktrees and Config (a title that changed left the strip measured for the old one), the active tab's title in bold cyan and every frame grey (`Palette.TabFrame`: `Tabs` draws a title with the Focus role and the lines with Normal; frames coloured per tab broke at the joins the tabs share), the table's header a closed box in the same grey with white names, holding one `TableBody<TState, TRow>` per view, the counts (`Wording.SessionCounts`, `WorktreeCounts`, `ConfigCounts`; the STATE words they and the STATE column share are `Wording.StateWord`) after the titles and the table's title right-aligned on the same row (a filter being typed before it, cut at its end), and the two-row key bar (`Wording.SessionsBar`, `WorktreesBar`, `ConfigBar`, placed `KeyBarItem`s drawn as clickable label pairs with tooltips) at the bottom.
- Left and Right (`TabKeys.TryFor`) step between the tabs as `NextTab` and `PreviousTab` (the digits were dropped in 0.20.0-preview.14; `SelectTab` is now only Esc and a click on a title, and the smoke script steps with the arrows), and `<` and `>` (`ScrollKeys.TryFor`, beside `TabKeys`) scroll a table's columns (`ColumnSizing.Scroll`, called by `TableBody`), because Shift+Left and Shift+Right never reached Cader in Windows Terminal though they worked headless.
- `ConsoleState` holds every tab's state and the active tab. `ConsoleComposition` hands the console one `ScreenContext` (the tab title, the settings row, whether a release is known, the announcement of a newly found one, the clipboard and the diagnostic log).
- A table's title is a `TableTitle` fact (`ListSelection.Title(noun, labelOf)`) that `Wording.Describe` turns into words; the worktrees title counts its branch and origin rows apart as branches through `TableTitle.Apart` (`10 worktrees, 3 branches`, a count of none left out) and names the selected row by `WorktreeRow.Name`, its folder or, for a row with no folder, its branch.
- Worktrees rows are keyed by `WorktreeRow.Key` (the selection, the pane's answers): the folder for a worktree row, `<repository key>|branch|<name>` for a branch or origin row, whose `Placement` is `NoFolder` and whose `Path` is its repository. A repository's folder rows come before its branch rows.
- The BRANCH column (after HEALTH, `ColumnFit.Natural`) shows `WorktreeRow.Flag` as `Wording.BranchCell` in `Wording.ToneOf(BranchFlagKind)` through `CellPaint.Text`, blank in the row's colour for `None`; `WordingOfBranches` holds each flag's glyph, word, tone and the pane's reason (`Wording.BranchReason`). A branch or origin row's pane reads no git (its folder is the main checkout's): it shows the Branch line with the reason, the pull request, the Repository and the commits at risk, never Folder, Created or a listing.
- The REPOSITORY and WORKTREE cells are `Domain\WhereLabel` (repository and place `Inside` a repository, the repository's middle elided first, or the folder's label alone `Outside` one, which on the Sessions tab follows `Wording.FolderGone`'s mark for a `SessionLocation.FolderGone` row; REPOSITORY gives it no place; a branch or origin row's WORKTREE cell names its branch in the place, while a worktree's branch is the pane's) over `Domain\FolderLabel` through `Application\FolderLabels` (roots read per redraw from `CurrentSettings`), fitted to the width the screen hands its elastic column. Which column is elastic, capped (NAME at 28 cells) or right-aligned (AGE, LAST COMMIT) is the column's own ColumnFit in its definition's Columns, never read from a header's words.

## Refreshing

- The worktrees are scanned once as the console opens, whichever tab is shown, and that scan waits for the Sessions tab's first listing (succeeded or failed) through `Application\LatestSessions`, which holds the Sessions tab's latest listing for every scan, so a scan runs no `claude agents` of its own. After it the Worktrees tab rescans on every show, on F5, at the Worktrees refresh interval while shown (never on its timer while hidden) and for a change a folder watch heard whether shown or not, and `Application\RunningLoads` lets one scan run at a time (the console reserves one on the UI thread before `TriggerLoad` and starts nothing when it cannot, and the scan function is wrapped in its `Track`, so the reload after an action is counted but never skipped). Within a scan `WorktreeInventory` lists the repositories and inspects their live worktrees at most eight git reads at once (a slot pool per scan, a slot held only around one listing or one worktree's counts), then merges each repository's results in name order, so the rows and the orphans are what a serial scan gives.
- `TableBody` keeps a tab's state, reducer loop and effect routing; `ColumnSizing` owns its column styles, widths and offset, `TableToolTips` its header and row tooltips, and `DetailReader` the detail pane's requests. A tab's refresh is its definition's `TabRefresh` (`Never`, or `Every` an `Application\RefreshSchedule`, which the composition builds over `CurrentSettings.Value.SessionsRefresh` or `WorktreesRefresh` and the `TimeProvider`). `ConsoleScreen` keeps one ticker at the heartbeat's interval (`RefreshWhatIsDue`) that asks each schedule `IsDue()` (the sessions' whether shown or not, the worktrees' only while shown), reading the interval afresh at each ask so a saved setting applies on the next tick with no timer re-created, and `ListSessions` and `ScanWorktrees` tell the schedule `Started()` whenever they reserve a load (start-up, the ticker, a show, F5), so any of those pushes the next timed refresh back a whole interval; an interval of 0 (`RefreshInterval.Off`) is never due. The reload after an action calls `TriggerLoad` directly and tells no schedule. The heartbeat keeps its own timer.
- Changes on disc start a refresh too (refresh-on-change). `Application\WatchPlan.For` plans the folders to watch (the Claude folder's `sessions` and `jobs` for Sessions; each repository the latest scan found, its `.git` folder with subfolders, from `WorktreeInventory.Repositories`, and each repository root's top level for Worktrees), and `Application\ChangeWatches.Follow` keeps one `Ports\IFolderChanges` watch per planned folder (`Infrastructure\Files\FolderChanges` over `FileSystemWatcher`, a no-op for a missing folder), stopping those no longer planned; `ConsoleLoads.FollowChanges` runs it as the console opens and after each scan returns. `Application\ChangeFilter` decides from the changed name alone which changes count (a session's `.json`, a job's `state.json`, a worktree's record coming or going under `.git\worktrees`, a `HEAD` written, a root's folder coming or going, and every overflow; never the index, objects, references, logs or lock files, so git's everyday work and Cader's own scan start nothing) and tells the tab's schedule `RefreshSchedule.Changed()` from the watcher's pool thread. A pending change makes the schedule due half a second after the first change and at least a second after the tab's last start (`IsDue()` for either half, `IsDueForChange()` for a change alone, which the ticker asks of a hidden Worktrees tab), and `Started()` clears it, so a change during a refresh is followed by one more. A watch Windows refuses, or one that overflows, is recorded as `DiagnosticEvent` `WatchTrouble` naming only its `WatchKind`; nothing is read from any watched file. F5 is `RefreshKeys.TryFor`'s `RefreshShownTab`, marked `IRefreshesTab`, answered by every reducer ahead of filter typing; `TableBody` routes it (`EffectRoutes.Of`, held by `EffectRoutingShould`) to `ITabHost.RefreshShown`, which calls `ListSessions`, `ScanWorktrees` or `ReadConfig` for the shown tab.
- `DetailReader` asks only while its tab is shown (a hidden tab drawn alone lands on the shown one) and never makes a refresh wait, and the waiting spinner centres on the table, not the tab; its words are `Wording.WaitingText(ConsoleTab)` and a failed load's `Wording.LoadFailurePrefix(ConsoleTab)`.
- The Config tab is `ConfigView` over `ConfigRow`s (`ConfigRows.For(settings, SetupFacts)`, a case per setting, the last two (`CheckForUpdates` and `DiagnosticLog`) toggled in place by Enter, `DiagnosticLog` carrying only whether it is on, then one `Heading` the selection steps over (`ListPolicy.Selectable`) and any filter hides (`ConfigSection.Setup`; a second, `ConfigSection.Accounts`, heads the `Account` rows `AccountCatalogue` remembers, shown only when there is one, Enter renaming a label through `AskForAccountLabel` and `NameDialog`), then one `Setup` case per piece of setup, its key stable across a save; the Claude folder row (directly after Settings file) is `SetupState.Folder` over `Domain\ClaudeFolder`, read once at start by `SharedParts` from `CLAUDE_CONFIG_DIR` and handed to `ClaudeTranscripts`, `ClaudeSettings` and `SetupFactsReader`, and `c` and `f` act on the folder itself; the Diagnostic log file setup row reads as `SetupState.LogFile` while the setting is on and `SetupState.LogOff` while it is off, `ConfigRows` choosing from the setting, both carrying the `LogFiles` (`cader.log` and `cader.log.1`, each `Written` with its size or `Absent`) that `SetupFactsReader` reads through `IDiagnosticLogFiles`, and `ConfigRows` adds a `SetupItem.OlderDiagnosticLogFile` row (`SetupState.OlderLog`) after it only once the files are read and `cader.log.1` is `Written`; `f` on either log row and on Settings file raises `OpenFileInEditor` where every other path row raises `OpenFolderInEditor`, and `d` on either log row raises `ClearDiagnosticLog` (a dialog effect, confirmed in `DialogEffects`) or explains `NoLogToClear` or `LogFilesNotRead`, and on any other row `ClearsOnlyTheLog`); its setting rows are shown at once and the setup is read off the UI thread by `SetupFactsReader` each time the tab is shown and after every action its keys dispatch (`TableBody` reloads a tab when an effect settles, so a save or a clear of the log is shown at once) and on F5, and it has no refresh timer; Sessions refresh and Worktrees refresh sit after Default place, each a `ConfigRow` case opening a one-box dialog (`SettingsScope.SessionsRefresh` and `WorktreesRefresh`).

## Detail pane

- Under the Sessions and Worktrees tables `Tui\DetailPane` shows what the selected row does not: a definition's `Detail` is a `Tui\TableDetail<TRow>`: `Pane` over an `Application\Detail\IDetailSource<TRow>` (`SessionDetails` and `WorktreeDetails` over `DetailLoader`, whose every fact fails on its own as `Unavailable`), or `None` on Config, which adds no pane.
- `DetailReader` (built by `DetailReader<TRow>.For` from the definition's `Detail`, a no-op `None` for a tab with no pane) owns the pane, its `DetailRequests`, the key last asked for and the token that drops a read when the tab is disposed; `TableBody` adds its `Views` and compares its `Current` around a load.
- The source states the most lines it takes, so the pane has a fixed height per tab and the table never jumps; `DetailRequests` numbers the requests and shows only the newest answer for the selected row; `Wording.Detail` words a `DetailContent` (a session's facts in five rows of two columns, the left one two of the pane's three columns wide, then its Account line across the pane, six rows in all, `Wording.SessionFactRows`; a worktree's in four rows of up to three columns, `Wording.WorktreeFactRows`, then its commits or changed files) and `DetailLayout` sets it out at the pane's width. The help's Pane section comes from `Wording.SessionsPane` and `WorktreesPane`.

## Status line

- The status line is the console's, not a tab's: `ConsoleScreen` draws it under the settings row from the shown tab's `ITabBody.Status` and `Running`, with rows only while `State.Message` has words or an action runs (`StatusLayout.Lines` wraps it onto at most three, and the tab strip, counts and table title move down by that many).
- Its mark and colours come from `Wording.ToneOf` (a `StatusTone` per status message and outcome case, each chosen in `StatusTonesShould`), `StatusMark` and `StatusWordsTone`; the mark shares its cell with the spinner and hides while it spins, or it blanks it.
- The line starts at the settings row's indent (after the icon), and a blue ✕ after the last word (`StatusLayout.Closes`) and a success's ten seconds (`StatusLayout.ClearsBySelf` and `SuccessShownFor`) both reduce `MessageDismissed` in the tab that showed the message, which clears it only while it is still that same `StatusMessage` instance.
- A newly found release is the one message no reducer raises: `UpdateCheck.TakeAnnouncement` (`ScreenContext.TakeAnnouncement`) answers `StatusMessage.NewerReleaseFound` once, and `FrameChanged` hands it to the shown tab's `ITabBody.ShowMessage` before drawing the line, so it shows on the first redraw after the check.
- The detail pane closes the tab, and the reducers clear a message when the selection moves or the filter changes; no tab has a standing message: a Config row's description (`Wording.ConfigDescription`) is only its hover tooltip (`IScreenDefinition.RowTip`), and the Sessions tab's one row tip (`Wording.SessionRowTip`) is for a session whose folder has gone, which `SessionRowEnricher` decides through `IFolders` before asking git.

## Dialogs

- The new-session wizard is a reducer too (`WizardView.Reduce` over `WizardState`, opened on a `WizardOrigin`, `Anywhere` for `n` or `Fixed` on the worktrees row's folder for `n` on that tab (`WizardOrigin.In`), whose `Chosen` answers a `RepositoryPick`, returning a `WizardEffect` to launch, close or do nothing; `WizardEffect.None` and `WizardProblem.None` stand where a null would, as `StatusMessage.Blank` does), and its dialog is a binder: `WizardControls` holds the layout, each control event becomes a `WizardInput`, and the state is pushed back to the controls under a `binding` guard so the events that pushing raises are ignored.
- The wizard's form, top to bottom under the repository list, is the name, Where, the worktree base, Before branching (a three-option `OptionSelector` that starts on the saved setting and changes only that session; its caption and last option must show at 120 x 36, which the smoke script checks) and the opening prompt, so `WizardControls.FormRows` is 21 and the `AnchorEnd` offsets above the preview count from it; a fixed folder leaves Before branching out, as it does Where and the base. Enter moves Base to Before branching to Prompt (`WizardView.Next`).
- A dialog with rules gets a reducer the same way, as a setting's dialog does (`SettingsView.Reduce` over `SettingsState`, scoped by a `SettingsScope` to the one value the Config tab's row edits, and holding it inside the saved settings so `Settings.Validate` checks it, bound by `SettingsDialog` and `SettingsControls`). Every repository root row opens `SettingsScope.Roots`, all the roots one per line, where Browse (F3) runs Terminal.Gui's folder picker and `SettingsInput.FoldersChosen` adds each folder as a line for F5 to check; the worktree root's dialog has the same Browse for one folder, which replaces the field, and `SettingsState.Browses` says which dialogs have it. The Open folder with dialog browses (F3, `SettingsBrowse.OneFile`) only while Custom is chosen, with Terminal.Gui's `OpenDialog` in file mode showing folders and `.exe` files, the file chosen replacing the executable (`SettingsInput.FileChosen`); every dialog holds the Browse button and `SettingsDialog` shows it only while `Browses` is not `No`. As it opens, that dialog asks `Application\EditorPresets` off the UI thread which of VS Code, Visual Studio and Rider cannot be found, applies the answer as `SettingsInput.PresetsLocated` through `app.Invoke` only while it is open, and retitles the choices from `Wording.Describe(EditorPreset, PresetSearch)` (`Rider (not found)`).
