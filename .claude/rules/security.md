# Security and diagnostics

The detail behind the security and privacy invariants in `CLAUDE.md`.

## Programs and arguments

- Every program Cader starts is found once as it starts and run by its full path: `Adapters\Processes\ProgramLocator` searches the PATH folders (only full paths: `PathFolders.Searchable` is the one filter every PATH search applies, az.cmd's and the VS Code shim's included) for the `.exe` only (CreateProcess would otherwise look in the parent's current directory before the PATH for a bare name, so a `git.exe` planted in the folder Cader was started from would run; `ProgramLocatorShould` and the fact in the security review of 2026-10-29 cover it).
- `ClaudeExecutable.Locate` answers a `ClaudeLocation` (`Found`, `BatchFileOnly`, `Missing`), `Application\RequiredPrograms.Check` turns it and git's location into both paths or `Wording.ClaudeIsABatchFile`, `ClaudeNotFound` or `GitNotFound` (Claude Code's first), and the tool's `Composition\LaunchParts` prints that sentence and exits 1; `ProgramLocator.Locate` answers a `Ports\ProgramLocation` (`Found`, `Missing`), and `GitHubPullRequests`, `AzureDevOpsPullRequests` (through `AzureCliExecutable.Locate`), `WindowsTerminal` (wt.exe and the tab's pwsh.exe, which `WindowsTerminalArguments` names by its full path) and `Desktop` take a `ProgramLocation` and report a `Missing` one where it is needed.
- A folder reaches an editor as one element of an argument list built by `EditorCommand`, never through a command line or cmd.exe, and the locator never answers a `.cmd` shim. `IEditorLocator` finds a preset's real executable as a `ProgramLocation` (Visual Studio's through `vswhere -latest -property productPath`, run by its full path); `IDesktop` opens a file with its associated application (`OpenAsync` throws `NoApplicationException` for a file type with none, never for an address, and `ProgramNotStartedException` when PowerShell or the open script fails; the two handlers that open an address catch the latter into `NotOpened`, the others let it reach the screen as `Failed:`) or starts a program detached (`StartAsync`: through ShellExecute from the same cleaned `pwsh` child, with the executable and each argument as Base64 in its script, `StartProgramScript`, so it inherits none of the console's handles and gets no Claude Code markers, and a refusal is reported by Windows' sentence for its native error code alone); `IClipboard` is implemented over Terminal.Gui's `app.Clipboard` by `Tui\ScreenClipboard`, attached while a table screen runs.
- No batch file is ever given text from a person, a repository or a listing: a custom editor's executable must be a full path (`SettingsProblem.ExecutableNotFullPath`), and `Domain\BatchFileArgument.IsSafe` (letters, digits, space, dot, underscore, hyphen, slash) is the one rule for what `az.cmd` may be given, applied to the remote names in `RemoteRepository` and to the branch in `AzureDevOpsPullRequests` (`PullRequestGap.BranchNotGivenToAz`).
- A pull request's head commit comes from the host's listing and reaches git only through `Domain\CommitId.TryParse` (40 or 64 hex digits), so nothing else a listing says becomes a revision: `GitHubPullRequests` reads `headRefOid` from `gh pr list --json`, and `AzureDevOpsPullRequests` reads `lastMergeSourceCommit.commitId`, which Azure DevOps documents as "the commit at the head of the source branch at the time of the last pull request merge" ([GitPullRequest](https://learn.microsoft.com/javascript/api/azure-devops-extension-api/gitpullrequest), checked 15 November 2026), and which `az repos pr list --output json` returns in that REST shape, so for a completed pull request it is the head that merged. A missing, blank or unreadable one is `HeadCommit.NotRecorded` and the pull request is still listed. The Azure DevOps field is read from the documentation, not yet seen on a real repository (track-branches task 6.3).
- User text must never be interpolated into PowerShell source: a tab's script reaches `wt.exe` Base64-encoded for [`pwsh -EncodedCommand`](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_pwsh), and every value inside it (paths, ids, folder names, whole messages) is built by `TabScripts` and goes through `PowerShellScript.Quote`, which doubles all five characters [PowerShell reads as a single quote](https://learn.microsoft.com/powershell/module/microsoft.powershell.core/about/about_quoting_rules) (`'` and U+2018 to U+201B). `PowerShellQuotingShould` checks this against real `pwsh`. Every semicolon reaching `wt.exe` is escaped by `WindowsTerminalArguments` (`windows.md`).
- An opening prompt that starts with `-` is `LaunchProblem.PromptLooksLikeAnOption`.
- Release notes come from outside the program (the changelog at a release's tag on GitHub, the changelog beside the program): `Domain\ReleaseNotes.TryParse` drops every control character as it reads each line and keeps only headings and one-line entries, the dialog shows the lines as text, and the release page's URL is built from the version alone by `Application\ReleasePage`. The version list is the names of winget-pkgs' folders, kept only when they parse as stable versions.
- Windows Terminal's own `settings.json` is changed only by `Adapters\Terminal\TerminalSettings`, through one guarded write, only to add the entry of a Cader profile Terminal hides as deleted (`HiddenTerminalProfiles.Of`) or, with `--remove`, to take out an entry that is exactly the four-property entry setup adds (`TerminalProfileRecords.Read.Added`; an entry with any other property is the user's and stays), and only after `cader setup-terminal` has shown the entries and the user has agreed (or passed `--yes`). The write refuses a symbolic link or other reparse point (a dotfiles set-up; replacing the file would replace the link) and a read-only file, answering a `TerminalSettingsEdit` case for each, and setup gives the entries to add or take out by hand. It changes only the profile list's text, so every other byte, comments and a byte order mark included, stays as it was; it parses the new bytes with the same comment-tolerant reader and writes nothing unless the list is exactly the original elements in order plus the added ones (or minus the removed ones), and unless the file as read holds the list the text walker found (a file naming `profiles` twice does not); it writes beside the file, reads the file again and writes nothing when its bytes changed (most likely a save by Terminal; a save landing between that read and the replace is still lost, as Terminal does not lock the file); then it puts the new file in place with `File.Replace`, which keeps the file's creation time and access rules and keeps the file as it was beside it as `settings.json.<yyyy-MM-ddTHH-mm-ss>.cader.backup` (UTC), which setup names. Its `state.json` is only ever read.

## Processes and identities

- A process is ended only as a `Domain\ConfirmedProcess`, which `IProcessRegistry.Terminate` and `EndCleanly` require and only three doors make: `TryConfirm` for a listed id (the process started no later than the session's listed start, plus five seconds; close-empty lists the others in `Gone` and adopt answers `ProcessGone`), `TryConfirmClaim` for a tab's shell (the recorded start exactly, as `TabRegistration.TryConfirmShell` and `IsLive` check) and `TryConfirmParent` for a step of the walk up to Windows Terminal (a parent started no later than its confirmed child).
- `ProcessRegistry.WithProcess` finds the process to end with .NET 11's `Process.TryGetProcessById`, which answers false for an id that has gone (no exception to catch); a protected process found by it refuses the action with a `Win32Exception`, which stays caught. An id of 0 or less, which it throws for, never reaches it: each door needs a start time the registry read, and the registry reads none for such an id. No start sets `KillOnParentExit`: its job would end, with the console, the programs Cader starts to outlive it and any daemon a captured child starts (`windows.md`, checked 14 November 2026).
- A process's command line carries secrets, so `ProcessRegistry.UsageOf` reduces one with `ProgramLabel` to a package or executable name and answers only that `ProcessUsage.Label`; the command line never leaves the method, so nothing else can keep, log or show it.
- A `SessionId` is ASCII letters, digits and hyphens with a letter or digit first, so no id from the listing can be read as an option or hold a path separator; `TerminalTab` walks up from a `ConfirmedProcess` only through parents `ConfirmedProcess.TryConfirmParent` accepts (started no later than their child), so a reused parent id never names another tab's shell.

## Deleting folders

- A leftover folder is deleted only through `IFolderDeleter`, which only `WorktreeRemover` holds (`LayeringShould.HandTheFolderDeleterOnlyToWorktreeRemover`), only strictly inside a repository root or the worktree root (`RemovalReason.OutsideTheRoots`, never forced), and `RemoveWorktreeHandler` and `DeleteSessionHandler` read its existence and files (`Application\LeftoverFiles`) from the disc as the key is pressed.
- A worktree whose `.git` file points at a live registration of a repository outside the roots is `WorktreeHealthKind.Elsewhere` (`HealthReason.RepositoryOutsideRoots`), a real worktree to the keys but refused removal with `RemovalReason.RepositoryOutsideRoots`, never deleted as a leftover; so is any `.git` file whose target exists (a bare repository's worktree, a `--separate-git-dir` checkout), its repository read from the gitdir's shape and a relative gitdir from the `.git` file's folder.

## Diagnostics

- Diagnostics live in `Application\Diagnostics`: one `DiagnosticLog` (the latest 500 events in memory, each also written to `%LOCALAPPDATA%\Cader\cader.log` by `Adapters\Diagnostics\DiagnosticFile` while the `diagnosticLog` setting is on, which the file's `DiagnosticLogSwitch` answers on every line, rolling to `cader.log.1` at 10 MiB), `ProcessCounts` filled by `RecordedProcessRunner` around the one process runner (which records a program that cannot start once per command and folder until that command starts there again, the folder held only as an in-memory key and never recorded), `RefreshCounts` (timed in `ConsoleLoads` and `PullRequestCatalogue`) and `StallCounts` (filled by `Heartbeat`, whose freeze line names the longest piece of UI-thread work marked through `Heartbeat.Mark` since the beat before, as a `CodeName` and a duration, or says none ran), the three held in one `PerformanceCounts` (each a `DurationSample`: runs and longest over every run, median and 95th percentile over the latest 1,000) and written to the sinks every 10 minutes by `PeriodicCounts` (always ticking, so a mark reaches the file only while the setting is on) and at exit, each count line saying `since start` because its figures cover the whole process, never one interval, and `CrashRecorder` writing `%LOCALAPPDATA%\Cader\last-crash.log`.
- The log files are deleted only by `IDiagnosticLogFiles.Clear` (`Adapters\Diagnostics\DiagnosticLogFiles`), which takes no path and deletes only `cader.log` and then `cader.log.1` (named once, by `DiagnosticFile.OlderPath`) at the path it was built with, which `SharedParts` gives it (`%LOCALAPPDATA%\Cader`) and `SceneHost` its scene folder; `last-crash.log` and every other file stay, and a file another program holds open is kept and counted, never an error. Only `ClearDiagnosticLogHandler` calls it, after `d` and its confirmation, and records the clear as `DiagnosticLogCleared` (files, bytes and files kept, never a path).
- A new fact is a new `DiagnosticEvent` case whose members are numbers, durations, versions, enums, `CodeName` (built only from a `Type` or `MethodBase`), `ExceptionSummary` (types, Windows' error number for a `Win32Exception` and frames, never the message) or `ChildCommand` (subcommand words from `ChildCommandWords` only), which `Architecture\DiagnosticEventsShould` enforces, and `DiagnosticsPrivacyShould` runs the daily flows over Northwind fixtures and fails on any fixture value in the output. Never log an effect's `ToString()`, an exception's message, program output or anything typed.
- The rendered lines (`DiagnosticLine`) are the one text outside `Wording`: they are a maintainer's format, not interface text. Each line, in the file, the crash file and a problem report, carries Cader's own process id in brackets after its UTC time, read from `Environment.ProcessId`, so the lines of several Cader processes sharing `cader.log` can be told apart; it is the one id a line may hold, and the process's `started` line gives its version. Terminal.Gui's logger is `TerminalGuiBridge`, which keeps only the level, the code name of the method that raised it (the first stack frame outside the bridge, `Microsoft.Extensions.Logging` and Terminal.Gui's `Logging` class, which `Program.cs` hands it as a `Type`) and an exception summary, Warning and above, because its messages can quote typed or pasted input.
