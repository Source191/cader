- `.github\workflows\mutation.yml` runs Core's mutation tests on a Windows runner, never on a pull request and never on the path of a merge or a release: after `pipeline` finishes on `main` for a push (`workflow_run`, so a release made with the workflow's token, which raises no `release` event, is still seen), only when the commit carries a `v*` tag (otherwise a notice and stop); every Sunday at 03:00 UTC; and by `workflow_dispatch` (usable only once the file is on `main`). One `mutation` concurrency group without cancel-in-progress runs one job and queues one. The job holds `contents: read` and `actions: read` and no secret; it restores `pipeline`'s NuGet cache read-only, runs `dotnet tool restore` and `dotnet stryker`, appends `mutation-report.md` to the job summary and uploads `stryker-output` and the small `mutation-results` (`run.json` and the cut report) for 30 days.
- The range (`Resolve-MutationRange.ps1`): after a release, `--since` the head commit of the newest finished mutation run on `main` (success or failure; a `workflow_run` counts only if its own commit carries a `v*` tag, since one that stopped at the notice mutated nothing; a schedule or dispatch run always counts) that is an ancestor of the release, so a run replaced in the queue never loses its changes; failing that, the previous `v*` tag; failing that, all of Core. A schedule or dispatch run has no range.
- A finding (`Write-MutationRun.ps1`): after a release, any `Survived` or `NoCoverage` mutant in the changed code that Stryker did not mark `static` (a static one is left to the weekly full run: `run.json` records how many as `staticSetAside`, and the comment names the number under its table; see skip-static-mutants-in-release-runs below); after a full run, a whole score more than 0.5 points below the previous full run's, read from that run's `mutation-results` artefact (skipped with a notice when it has expired, the run then being the baseline). A job of its own, `report`, which holds only `issues: write` and runs nothing from the repository, posts the comment the mutation job wrote (`Format-MutationComment.ps1`: the release, range and run link and at most 50 mutants, or both scores and the five files that fell most; cut to 60,000 characters) on the open issue labelled `mutation`, or opens one assigned to `vars.MUTATION_WATCHER`. The issue stays open until the owner closes it. The strict release rule: a release run that counted at least 20 mutants (Killed, Timeout, Survived and NoCoverage, what the score is over; `-MinimumCounted`, default 20, because a run of a few mutants scores 0 or 100 on one change) and left any Survived or NoCoverage that is not static is `Failing`; `run.json` records `counted` and `failing`, the comment opens with "This run failed" and the count, and the job's last step, after both uploads, runs `exit 1`. An Ignored (marked) mutant counts for nothing, a smaller run only comments, and a full run never fails this way. It was switched on once a runner full run left no unmarked survivor (close-mutation-gaps 9.1); `Mutation.Tests.ps1` holds the edges (20 with a survivor fails, 19 does not, 20 with none passes) and the workflow step by reading `mutation.yml`.
- Before publishing: `publish.yml`'s `mutation-notice` job (no environment, `contents: read` and `issues: read`, no secret) runs before the owner's approval, lists the open issues labelled `mutation` with `gh` and prints a `::warning::` and a job summary section naming them (`Get-MutationWarning.ps1`); it never fails or blocks, and `test\Scripts\Get-MutationWarning.Tests.ps1` holds the script and the job's rights.
