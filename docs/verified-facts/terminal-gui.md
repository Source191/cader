# Terminal.Gui 2.5.0: the evidence

Moved from `.claude\rules\terminal-gui.md` on 22 November 2026 (slim-claude-context) as it stood; the rule is still `.claude\rules\terminal-gui.md`.

## Terminal.Gui 2.5.0 facts, as they stood

- **On .NET 11 (14 November 2026, runtime 11.0.0, SDK 11.0.100):** Terminal.Gui 2.5.0 ships only a `net10.0` library and runs on `net11.0` unchanged: the full test suite passed, and CI's smoke check opened and closed every screen and dialog on both architectures and the hand-off check attached and detached (run 43638076129). The facts below keep the dates they were observed on; none was re-observed by hand on .NET 11.
- Instance API: `Application.Create().Init()`, `app.Run(window)`, `app.RequestStop`, `app.Invoke`, `app.AddTimeout`; set `app.Driver.Force16Colors = false` or the palette collapses to 16 colours.
- Never block the UI thread on an awaited call (`GetResult()`): Terminal.Gui installs a synchronisation context and the continuation deadlocks. It showed only after an attach-and-return, which the console no longer does (a session opens in its own tab); the hand-off check was built because of it.
- Focus roles: a scheme with Focus equal to Normal hides focus everywhere; ListView draws the selected row with Focus when focused and Active otherwise; a TextField needs its own background or it is invisible when empty, and a read-only TextField is drawn with the ReadOnly role once it loses focus.
- Dialogs: a Button with IsDefault takes the initial focus; set focus from the dialog's `Initialized` event, not before `Run`. A Dialog of Height 12 has 8 usable rows and the button row overdraws the last. A Label that receives text later needs a fixed Height and non-empty initial Text. A TextField's Enter raises its own `Accepting`; KeyDown handlers on the field or dialog do not see it. Ctrl+C in a TextField copies its selection through `app.Clipboard`, which Windows Terminal passes through when it has no selection of its own.
- A Label reads `_` as its hotkey mark unless `HotKeySpecifier` is set to U+FFFF before `Text` (node_repl showed as noderepl). A Dialog holding one Label per line from Y 1 and a Button with its shadow row drew nothing in its last two content rows at Height lines + 6 (the same loss as a single multi-line Label through `Confirm.Ask`), so `MemoryDialog` uses lines + 8; this is two rows fewer than the "8 usable rows at Height 12" rule above allows, and the difference is unexplained.
- Keys: `KeyMapping.TryFrom` reads a printable character with `key.AsRune` (`KeyMappingShould` pins the keys the reducers use: the named keys (F5 among them since 0.22.0-preview.45), `d`, shifted `D` as a capital, space, `<`, `/`, `?`, and nothing for Ctrl, Alt, F1, Tab or a rune outside the basic plane). Terminal.Gui 2.5.0's `Key.TryGetPrintableRune` ("exactly one printable rune") reads the same keys in its XML docs, but whether it agrees with `AsRune` for Alt, AltGr and Ctrl chords has not been tried at a real Windows Terminal (the spike of the archived `table-body-collaborators` change was not run: it needs a person at the keyboard), so the swap was not made. Press Shift+letter, Ctrl+letter, Alt+letter, AltGr `€`, `<`, `>`, `/` and `?` at 120 x 36 and log both answers before changing the branch (2 November 2026).
- `View.RemoveAll()` returns the removed views and the caller owns them from then on, so `ConsoleScreen` disposes what it removes from the counts rows and the key bar; a tooltip set with `app.ToolTips.SetToolTip` stays registered for a disposed label until `app.ToolTips.RemoveToolTip(view)` unsubscribes it, so the key bar removes each label's tooltip first (Terminal.Gui 2.5.0 XML docs, 2 November 2026; the smoke check rebuilds the bar on every tab and filter change).
- Tooltips: `app.ToolTips.SetToolTip(view, text)` shows on hover (the label's MouseEnter), anchored under the pointer's view. A table raises no position reports unless `MousePositionTracking` is true, and its tooltip is evaluated only on entry, so the column-header tooltip is shown by hand (`ApplicationToolTip.ShowFor` from `table.MouseEvent` with `ScreenToCell(position, out header)`, hidden on leaving the header); Terminal.Gui draws a tooltip at its target's bottom-left (`ToolTipHost.SetPosition` over `FrameToScreen`), so under the whole table it covered the detail pane, and `TableToolTips` targets a zero-width `Anchor` view laid over the header (or, for a Config row's description from `IScreenDefinition.RowTip`, over the row) at the pointer's column, which puts it on the rows just under. It still shifts a wide tooltip left to fit the screen. Each showing calls the provider's factory for a new content view, and `ToolTipHost` disposes the view it replaces and, when disposed, the one it holds, so `ToolTips.View`'s labels need no disposing by the caller (read from the 2.5.0 assembly, decompiled with ilspycmd, 16 November 2026). The headless terminal can hover: send SGR motion `\u001b[<35;col;rowM` (1-based) after 8000 ms.
- The help is `Tui\HelpDialog`: a read-only `TextView` in a dialog as tall as the text needs, up to nine tenths of the screen, with focus in the text so the arrow keys and PageUp and PageDown scroll it. A Dialog reserves its own button area, so the box is `Y = 0` with `Dim.Fill()`; reserving rows for the button as well cuts the last lines. The sessions help (26 lines) fits whole at 120 x 36.
- Removing a SubView from `Tabs` selects another and raises `ValueChanged`, so `ConsoleScreen` disposes its tabs under the binding guard, or quitting shows (and logs) the other tabs.
- `OpenDialog` (`OpenMode.Directory`, `AllowsMultipleSelection`) is the roots dialog's folder picker, checked by a spike on 30 October 2026: it derives from `Dialog<IReadOnlyList<string>>`, not the plain `Dialog`, so `DialogTabTitle.Apply` takes a `Runnable`, and it writes its own title as the tab title like any Runnable. It opens at 96 x 28 in a 120 x 36 terminal and takes `Palette.Focusable` for most of its parts. Focus starts in its path box; Tab reaches the folder list, Down moves the selection (the path box follows), Shift+Down extends it, Enter in the list confirms rather than opening the folder, and Space does not toggle a row. `FilePaths` answers the folders in the order chosen (`Path` is empty for several), and `Canceled` is true after Esc. The headless terminal drives it.
- `OpenDialog` in `OpenMode.File` is the Open folder with dialog's picker for a Custom executable. Read from the 2.5.0 assembly (decompiled with ilspycmd, 1 November 2026), not observed: `AllowedTypes` is a `List<IAllowedType>`, and `new AllowedType("Programs", ".exe")` matches by the path's ending, ignoring case; with any allowed type in File mode the list shows folders and only the files that match (`FileDialogState.GetChildren`), the first type becomes the filter and a types drop-down is shown, and accepting a typed path of another type is refused in the dialog with its own wrong-type line. `MustExist` defaults to false, so a typed path that does not exist is accepted (F5 checks it), but a folder typed in File mode is refused. Enter on a folder in the list opens it and on a file accepts it; `Path` is the path box's text (set before `Run` it opens there; left empty it becomes the current folder at `EndInit`), and with one file allowed `FilePaths` answers `[Path]` once accepted and an empty list otherwise; `Canceled` is `Result == null`, which the Cancel button and Esc leave. `OptionSelector.Labels` has a public setter that disposes and rebuilds every option (`SelectorBase.CreateSubViews`), so the dialog retitles the existing options' `CheckBox`es instead, which keeps focus where it is.
- `app.AddTimeout` callbacks keep running at their interval while a modal dialog runs its own `app.Run`, so the console's refresh timers and `Heartbeat` tick under a dialog. Observed on 1 November 2026 with Terminal.Gui 2.5.0 (a throwaway program in the headless terminal: a 250 ms timeout beat 18 times, about 280 ms apart, during a 5-second dialog opened by a key) and read from the decompiled assembly: the application has one `TimedEvents`, the nested `ApplicationImpl.Run` loops `Coordinator.RunIteration()` like the main one, and `ApplicationMainLoop.IterationImpl` ends with `TimedEvents.RunTimers()` whichever runnable is on top. `RunTimers` holds its lock while it calls each callback, and `app.Invoke` from another thread is `TimedEvents.Add(TimeSpan.Zero, ...)`, so a dialog opened from inside a timeout callback blocks every other thread's `app.Invoke` until it closes (observed: the background close request never returned), and by the same reading so does one opened from inside an `Invoke` callback, which runs as a zero timeout (read, not observed); the UI thread re-enters the lock, so timers still fire.
- A `Dialog` run as the application's first runnable, before the main window (the What's new dialog on the first start of a new version), raises `IsModalChanged` with true like any dialog, so `DialogTabTitle` writes its tab title, and the window run after it writes its own (observed 1 November 2026, Terminal.Gui 2.5.0: a throwaway program in the headless terminal wrote `Initialized`'s title, then the modal title, then the window's; Esc closed the dialog and the window followed). The `count` command reads plain text only, so a title is found in `drive-raw.txt` itself or by a smoke step's title marker.
- Read from the decompiled 2.5.0 assembly (ilspycmd, 15 November 2026), not observed: `app.Run` raises a dialog's `Initialized` synchronously before its first draw (`Runnable.RaiseIsRunningChangedEvent` calls `BeginInit` and `EndInit` when it is not yet initialised, and `View.EndInit` ends its SubViews first, then raises `Initialized`), so a binder's `Push` from `Initialized` always runs. `TextField.OnKeyDownNotHandled` inserts any key with a grapheme except a control rune, a Ctrl chord or an Alt chord without one, so a space or a format character such as U+200B typed or sent into a filter is kept and draws as blank, so both filters (the wizard's and the tables' `/`) ignore leading blank, control and format characters when matching (`CharacterKinds.WithoutInvisibleStart`).
- Read from the decompiled 2.5.0 assembly (ilspycmd, 15 November 2026), not observed: `Logging.Warning`, `Error`, `Critical` and their siblings take `[CallerMemberName]` and `[CallerFilePath]` and put the caller's file and member only inside the message text (`[File] [Member] message`), then call `LogWarning(string)` and its siblings on the current logger, so a logger is never given an `EventId` other than 0 (the assembly references no `EventId` at all). The logger `Logging.Logger` is a global, and `Logging.PushLogger` sets one for the current async flow alone (an `AsyncLocal`), which tests use. `TerminalGuiBridge` therefore reads the raising method from the call stack, skipping its own frames, `Microsoft.Extensions.Logging`'s and `Logging`'s, which `Program.cs` hands it as a `Type` because Core cannot reference Terminal.Gui (a name constant holding `Terminal.Gui` fails `LayeringShould.KeepTerminalGuiInsideTui`).
- `TextView` is obsolete (pragma CS0618) but still the wrapping multi-line box. `OptionSelector` replaces RadioGroup. Table rows take colours through `TableView.Style.RowColorGetter`.
- `Tabs` (no `TabView` or `TileView` in 2.5.0) shows each SubView as a tab titled by its `Title`; the strip takes three rows (outer border, titles, separator) and the selected tab's body starts on the fourth, framed. Its span is each title's length plus a border cell either side, adjacent tabs sharing one (`GetTotalHeaderSpan` is private, though each header's place and width are public as `BorderView.TabOffset` and `EffectiveTabLength`, read 20 November 2026), so the counts label sits after it on the title row. The selected tab is the focused SubView, so a tab's view has `CanFocus = true`; setting `Value` and clicking a title both raise `ValueChanged`, so the console applies a click under a binding guard. A spinner redraws only its own tab, title box and frame included, which lands on top of the shown tab and closes its edge under the title (the Worktrees tab's waiting spinner, which turns while its first scan runs and the tab may be hidden, did this from the first frame), so `ConsoleScreen.Show` tells both tabs which is shown (`ITabBody.Shown`) and a hidden tab keeps its spinners still; a table refresh is safe because `FrameChanged` redraws the whole window. It binds the arrow and paging keys to moving between tabs, which took Up and Down from the table, so `ConsoleScreen` removes those bindings from the strip and both tab views; every other key still reaches the window's `KeyDown`. `Shortcut` draws its command text before its key (`Attach  Enter`) with Terminal.Gui's own key names, so the key bar is label pairs with `MouseEvent` handlers on `MouseFlags.LeftButtonClicked` instead (checked by a spike, 30 October 2026).
- A `Tabs` title that changes (20 November 2026, Terminal.Gui 2.5.0 on SDK 11.0.100; "read" is from the assembly decompiled with ilspycmd, "observed" from a throwaway program in the headless terminal at 120 x 36; Windows Terminal 1.25.3131.0 was not used, so colour and glyph width there are not yet observed):
  - **Re-measuring:** `View.Title`'s setter calls only `SetNeedsDraw`, and each tab's header is a `TitleView` inside its `BorderView` whose text and width are set only in a layout pass (`BorderView.OnSubViewLayout` calls `TitleView.UpdateLayout`, which sets `Text` and `MeasuredTabLength`), so with no further call the strip keeps the old title and width (read and observed). `Tabs.OnSubViewLayout` places the tabs (`UpdateTabOffsets`, from `BorderView.EffectiveTabLength`) before its SubViews re-measure, so one `SetNeedsLayout` on the strip or the tab re-measures the changed title but leaves the tabs after it placed for the old width, one change behind: grown, the long title showed through under Worktrees and cut Config to `1 ■4` (observed). Two public ways come out right at once (observed): `tabs.SetNeedsLayout(); tabs.Layout(); tabs.SetNeedsLayout();`, or setting the public `BorderView.TabLength` (reached as `(BorderView)tab.Border.View`) to the title's width plus two, whose setter lays the strip out again. Neither changed the shown tab or its focus, and neither raised `ValueChanged` (observed, grown and shrunk with Worktrees shown).
  - **Colour:** by default a title is one `TextFormatter.Draw` in Focus (shown tab) or Normal (hidden), with only a hot-key character in HotFocus or HotNormal (`View.DrawText`, read). The header is a public `View` (`BorderView.TitleView`) whose `DrawingText` can be cancelled and the title drawn in parts with `Move`, `SetAttribute` and `AddStr`: the capture held `Sessions ` in cyan, `◐3 ` in amber and `✗1` in red, and kept them when the tab was hidden (observed headless, as escape sequences; not seen in Windows Terminal).
  - **Glyphs:** `◐ ● ✓ ✗ ■` measure one cell each in a title (a 23-character title made a 25-cell header, and the headless strip lined up), observed headless only.
  - **Movement and clicks:** every tab after a title moves with it, and a click selects the tab whose header is under the pointer as drawn, raising `ValueChanged`: with the pointer resting on Config, Sessions grew by ten cells and the click selected Worktrees (observed). Titles wider than the strip scroll it to keep the selected tab whole (`EnsureTabVisible`, read), cutting the first titles off and showing a `◄` scroll button (observed).
  - **Overlay:** text drawn from a tab's `DrawComplete` on its frame's top edge (the row under the titles) never showed, because `Tabs` renders the tabs' shared line canvas over it (`SuperViewRendersLineCanvas`); text on the titles' row after the strip survived a tab switch, a retitle and a spinner on the hidden tab, while that spinner still closed the shown tab's edge as the fact above says (observed).
  - **Cost:** each title change with the two-pass layout redrew the window, the strip and every tab, the hidden ones included (30 changes at ten a second: 30 draws of each, about 4 KB of output per change at 120 x 36), the same as a table refresh already does; whether it flickers in Windows Terminal is not observed.
- A table that cannot take focus draws its selected row with the scheme's Active role, which Terminal.Gui derives as a lighter shade when a scheme leaves it unset (black on cyan came out as bold dark grey on bright cyan, a red block as pink): `Palette.SelectedRow` names those colours and sets every role, and a cell that keeps its own colour there (the TAB block, `CellPaint.Fill`) is drawn with `Palette.SelectedRow(colour)`.
- `SpinnerView.AutoSpin` is safe to set repeatedly and before the view has an `App` (`EndInit` adds the timeout later); the default style is Line, and `SpinnerStyle.Dots` renders in the headless capture.
- `ImageView` (Terminal.Gui 2.5) takes a `Color[,]` and draws it through [Sixel](https://vt100.net/docs/vt3xx-gp/chapter14.html) or [Kitty](https://sw.kovidgoyal.net/kitty/graphics-protocol/) when the driver reports support (`app.Driver.SixelSupport`, detected at start-up; Windows Terminal draws Sixel), fitted to the view at `ZoomLevel` 1; without support it colours one cell per pixel, so `LogoIcon` stays hidden then. The icon's pixels are `assets\icon\logo-48.rgba` (`*.rgba binary` in `.gitattributes`), written by `tools\New-IconPixels.ps1` (the icon from `LogoMark.ps1` with `-Outline`, an edge in the frames' grey drawn inside its dark tile, which otherwise vanished on the console's black; white was too stark and the mark without its tile, `-NoTile`, read worse; `LogoIcon.Fit` makes the view as many cells wide as its one row is tall in pixels, from the reported cell size, because a fixed width stretched the icon) and embedded in the Tui assembly; the headless terminal reports no image support, so its captures never show the icon.
- A program that runs `ConsoleScreen` cannot reach its `IApplication` (`Run` creates it with `Application.Create().Init()`), so `NewKeyDownEvent` is not available from outside. Writing key events into the program's own console input with `WriteConsoleInputW` (each a KEY_EVENT record with the virtual key, scan code and character, down then up) is read by Terminal.Gui as typed keys: `/` then `stock` filtered the Sessions table (observed 4 November 2026, Terminal.Gui 2.5.0 in Windows Terminal 1.25.2733.0, from `tools\ReadmeScene`, with the window neither focused nor needing to be).
- `TableView` (read from the decompiled 2.5.0 assembly with ilspycmd, and observed in the README scene in Windows Terminal, 18 November 2026): with `ShowVerticalCellLines` off and `SeparatorSymbol` a space, `RenderRow` writes a blank in the cell's own attribute at each column's last cell (`X + Width - 1`), and `TruncateOrPad` cuts a cell as long as its column to one character fewer, so text drawn cell by cell always breaks between columns; a line across the row is drawn from the table's `DrawComplete` instead (`ColumnSizing.DrawHeadings`, with `Move`, `SetAttribute` and `AddStr`). With the header's outer vertical line shown, the first column starts at `X` 1, so `ScreenToCell(0, y)` answers null for every row; ask at the right edge for the row and scan from the left for the first cell. `CalculateMaxCellWidth` measures every rendered row's cell, so a cell left empty never widens its column.
- `ViewArrangement.TopResizable` on a view inside a `Tabs` tab (observed 20 November 2026, Terminal.Gui 2.5.0, a throwaway program in the headless terminal: a `TableView` with `Height = Dim.Fill(11)` and a pane of `Y = Pos.AnchorEnd(11)`, `Height = 11`, `BorderStyle = LineStyle.Single` and `Border.Thickness` top only, driven by SGR press, motion with the button held and release): a press on the divider row and motion drags the top edge one row per report, and a press on any other row of the pane reaches the pane's own `MouseEvent` instead and drags nothing; nothing extra is drawn on the divider (no arrange buttons, before, during or after the drag). Each step raises the pane's `FrameChanged` with the new frame while `Y` and `Height` still read the old values, and the drag leaves them absolute (`Y = Absolute(18)`, `Height = Absolute(15)` after four rows up), not anchored, and leaves the table's `Height` alone, so the pane covers the table's last rows. The arranger keeps writing `Y` and `Height` from the pointer after a `FrameChanged` handler returns, so a value set inside the handler (or through `app.Invoke`, which ran before the arranger's write) is overwritten and the drag ignores any limit; a value set from `app.AddTimeout(TimeSpan.Zero, ...)` lands after it, so re-anchoring there (`Y = AnchorEnd(h)`, `Height = h`, the table `Dim.Fill(h)`) leaves the pane anchored and clamped once the pointer stops, at the cost of one frame drawn past the limit while dragging. Ctrl+F5 (Terminal.Gui's arrange key) reached the window's `KeyDown` and entered no arrange mode for the pane, which cannot take focus, so no key the console uses enters it. A window resize after a drag was not observed (the headless terminal keeps its size): with the pane re-anchored it is laid out by `AnchorEnd` as before the drag (read, not observed). resizable-detail-pane, which would have used it, was withdrawn on 20 November 2026.
- `TableView`'s scroll (read from the decompiled 2.5.0 assembly with ilspycmd, and held by `TableScrollShould` over a real table, 19 November 2026): setting `Table` calls `SetSelection(0, 0)` and then `Update()`, whose `EnsureCursorIsVisible` scrolls to that first cell, so every source swap put the view back at the top; `SetSelection` never scrolls; `RowOffset` is `Viewport.Y` less the header's height once headers scroll away (`AlwaysShowHeaders` off), and though `TableView`'s own setter does not clamp, `View`'s `Viewport` setter keeps it within the content while `ViewportSettings` is `None` (a throwaway program, 19 November 2026: 88 on 35 rows reads 23), so `EnsureValidScrollOffsets` is a second guard. `Tui\TableScroll` therefore reads `RowOffset` before the swap, puts it back, calls `EnsureValidScrollOffsets`, and calls `EnsureCursorIsVisible` only when the selected key or the filter changed; `ColumnSizing.RestoreOffset` runs after it, because `EnsureCursorIsVisible` also scrolls back to the cursor's first column.
- The new-session wizard's chrome (observed 22 November 2026, Terminal.Gui 2.5.0, Debug builds of Cader 0.22.0-preview.54 in the headless terminal at 120 x 30, 36 and 40): a `Dialog` with buttons takes six rows of its `Height` besides its content (the top and bottom border, a button area of a blank row, the buttons and their shadow row, and the dialog's own shadow row under its bottom border, which draws nothing in a plain capture, so the frame drawn is one row shorter than `Height`), and a `Pos.AnchorEnd(2)` control sits on the content's last two rows. `Dim.Percent(90)` (32 and 36 rows at 36 and 40) left the repository list, under the caption and the filter and over the 21-row form, three rows and seven, and at 36 its `Dim.Fill(FormRows, 4)` minimum put its fourth row under the Session name caption; an explicit `Height` of 30, 34 and 38 drew frames of 29, 33 and 37 rows with lists of one, five and nine rows, which `WizardFit` pins.

## Terminal.Gui 2.6.0

Re-checked on 22 November 2026 with Terminal.Gui 2.6.0 (merged in PR #386, 0.22.0-preview.54) on SDK 11.0.100, for the `adopt-terminal-gui-2-6` change. "Observed" is a throwaway console program referencing 2.6.0, run in `tools\HeadlessTerminal` at 120 x 36 and deleted afterwards; "read" is the 2.6.0 `net10.0` assembly decompiled with ilspycmd.

- **A dialog inside a callback no longer blocks `Invoke` (P1, observed).** A dialog opened inside an `app.Invoke` callback stayed open for 4 s; 1 s after it opened, a pool thread called `app.Invoke`, which returned in 2 ms, and its callback ran on the UI thread 30 ms after the call, with the dialog still open. The same with the dialog opened inside an `app.AddTimeout` callback: the call returned in 1 ms and its callback ran after 32 ms. On 2.5.0 the same call never returned until the dialog closed (the timers bullet above). This is tui-cs#5655: timer callbacks run outside the queue's lock, one at a time behind a re-entrant gate. The dialog's own `app.Run` installed `MainLoopSyncContext` in both cases.
- **Timers still tick under a dialog (P2, observed):** a 250 ms timeout beat 18 times during a 5-second dialog opened by a key (45 in all over the 14 s run), as on 2.5.0.
- **A spinner on a hidden tab no longer closes the shown tab's edge (P3, observed):** `Tabs` with Sessions, Worktrees and Config, Sessions shown, and a Dots `SpinnerView` turning on the hidden Worktrees tab for 4 s. Every one of the capture's 43 redraws of the separator row left the shown tab open under its title (`││        ╰─────────┴──────┴───`), the same row as with the spinner still; no redraw closed it. This is tui-cs#5777 (`RedrawsCleanSubViewBorders`). The cost is still there: the turning spinner made the window, the strip and every tab redraw on each frame (43 full redraws, 43 KB of output in 4 s, against one redraw and 5 KB with it still), so `TableBody` keeps a hidden tab's spinners still.
- A dialog opened inside an `app.Invoke` callback blocks every other thread's `app.Invoke` until it closes (observed 22 November 2026, Terminal.Gui 2.5.0 on .NET 11, a throwaway program in the headless terminal: a second thread's `app.Invoke` call returned only when the dialog closed, 4.1 s later). So no pool thread doing real work calls `app.Invoke`: a launch's step is picked up by the console's ticker instead (guard-overlapping-actions).
