# Windows processes: the evidence

Moved from `.claude\rules\windows.md` on 22 November 2026 (slim-claude-context) as it stood; the rule is `.claude\rules\windows-processes.md`.

## Windows process facts (verified 2026-10-29, Windows 11 26100), as it stood

- A process's memory for the detail pane's Memory line and the `m` breakdown is its private working set, read with [`GetProcessMemoryInfo`](https://learn.microsoft.com/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo) and [`PROCESS_MEMORY_COUNTERS_EX2`](https://learn.microsoft.com/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) (`PrivateWorkingSetSize`): the figure Task Manager's Memory column and the `Working Set - Private` counter show. It counts resident pages only: an MCP server idle for hours reads a few kilobytes against 90 MB of commit (`PrivateUsage`, the same structure) because Windows has paged its heap out, and thirty node processes share the runtime's image pages, so summing working sets (`WorkingSet64`) doubled a tree's figure. A megabyte is 1,048,576 bytes throughout.
- [`Process.GetProcessById`](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.getprocessbyid) walks the whole process table on every call, about 20 ms: measuring six sessions' 235 processes through it took 4 to 6 s per refresh, against 40 to 230 ms through [`OpenProcess`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-openprocess) with [`PROCESS_QUERY_LIMITED_INFORMATION`](https://learn.microsoft.com/windows/win32/procthread/process-security-and-access-rights) and [`GetProcessTimes`](https://learn.microsoft.com/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes) (which also reads processes a full-access handle is refused for). Every read in `ProcessRegistry` (`StartTimeOf`, `ParentOf`, `UsageOf`) opens its own limited handle, and `GetProcessById` is used only to end a process. `NtQueryInformationProcess` with `ProcessBasicInformation` (the parent id) and [`QueryFullProcessImageNameW`](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew) (the executable name) answer through that same limited right (checked 2026-11-02, Windows 11 build 26100, 0.20.0-preview.27); `ProcessRegistryIntegrationShould` keeps two hundred start times, parents or usages each under a second.
- [`CreateToolhelp32Snapshot`](https://learn.microsoft.com/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot) lists every process with its parent's id in a few milliseconds without opening any; the parent id is never cleared when the parent exits, and Windows reuses ids, so a process may list a parent younger than itself (an installer-launched app sat under a session's reused id during the spike). `ProcessTree` keeps a child only when it started after its nearest measured ancestor.
- **A fetch that needs credentials (checked 14 November 2026, git 2.56.0.windows.4 with Git Credential Manager 2.9.1, by the owner; the design assumed git 2.55):** `git fetch origin +refs/heads/main:refs/remotes/origin/main` against an HTTPS remote with no stored credential (a private-looking GitLab URL), run with `GIT_TERMINAL_PROMPT=0` and [`GCM_INTERACTIVE=false`](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/environment.md), its output captured and stdin from nul, exited 128 in 0.85 to 0.95 seconds with the stderr `fatal: Cannot prompt because user interactivity has been disabled.` and `fatal: could not read Username for 'https://gitlab.com': terminal prompts disabled`; watched twice, no window or prompt appeared. So `GitCli.FetchBranchAsync` sets both in its request's `Variables`, which `ProcessRunner` applies after the `InheritedEnvironment` drop, and a fetch that needs signing in fails at once (fetch-before-branching's design decision 2). Cader's captured runs leave stdin inherited rather than nul. An SSH key's passphrase prompt is not covered and waits until the 60-second limit.
- **.NET 11's process APIs (checked 14 November 2026, runtime 11.0.0, Windows 11 26100, `ProcessApisShould`):** [`Process.RunAndCaptureTextAsync`](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.runandcapturetextasync) and `RunAndCaptureText` end only the child (`Process.Kill()`) on cancellation or timeout, so a grandchild keeps running and holding the redirected pipes; `ProcessRunner` keeps its own `Kill(entireProcessTree: true)`. [`KillOnParentExit`](https://learn.microsoft.com/dotnet/api/system.diagnostics.processstartinfo.killonparentexit) puts the child in a kill-on-close job, so killing the parent ends every descendant in it, one whose own parent had already exited and one started through ShellExecute included; on this machine (not elevated) a start under it was refused with Access denied (5) for the Microsoft Store PowerShell's and winget's app execution aliases in `%LOCALAPPDATA%\Microsoft\WindowsApps`, while the hosted x64 runner (Windows Server 2025, elevated) started its alias, so which machines refuse is unknown. Cader sets it on no start. `Process.TryGetProcessById` answers false for an id that has gone and true for the System process (4), which then refuses to be ended (`ProcessRegistry.WithProcess` uses it); `SafeProcessHandle.TryOpen` answers false for a gone id but throws `UnauthorizedAccessException` for System.
- **Redirected streams outlive the `Process` (measured 16 November 2026, Windows 11 26100):** a redirected stream the caller has read is not closed by `Process.Dispose` ([`Process.Close`](https://learn.microsoft.com/dotnet/api/system.diagnostics.process.close): the caller owns it once read). With 200 captured runs of `git --version` and the readers undisposed, 42 handles stayed open after a full collection on 10.0.15 and 434 on 11.0.0; disposing the readers left 1 on each. So `ProcessRunner.RunAsync` declares both readers with `using` straight after `Start`, and `ProcessRunnerIntegrationShould.CloseTheOutputPipesOfEveryCapturedRun` keeps 50 runs under 25 extra handles. Disposing a reader whose `ReadToEndAsync` is still pending, because an orphan the tree kill could not reach holds the pipe past `EndAsync`'s five-second wait, neither blocks the caller nor leaves an unobserved task exception: once the orphan ends, both reads end `RanToCompletion` (runtime 11.0.0, seen with a throwaway probe that kept the read tasks; `LeaveNoUnobservedFaultWhenAnOrphanHoldsAPipePastTheLimit`, which does fail for an injected unobserved fault).
- **Ending a tree (checked 14 November 2026, runtime 11.0.0):** `Process.Kill(entireProcessTree: true)` first lists every process to check the caller is outside the tree, then kills the root, then lists them again and ends, recursively, each whose parent id is the root's and whose start time is strictly later (`Process.NonUap.cs` and `Process.Windows.cs` at the commit Learn links). Start times are precise to well under a millisecond: over 100 runs here `cmd /c ping` started its ping 35 to 115 ms after cmd and never at the same moment. A grandchild left running by killing only the child holds its inherited redirected pipes open, so `ProcessRunner` would wait its five seconds for them before reporting the cancellation.
- [`NtQueryInformationProcess`](https://learn.microsoft.com/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess) with class 60 (`ProcessCommandLineInformation`) answers a process's command line as a `UNICODE_STRING`; asked with no buffer it answers `STATUS_INFO_LENGTH_MISMATCH` and the length. Command lines carry secrets (an MCP server's API key was in one), so `ProgramLabel` reduces one to a package or executable name and nothing else is kept, logged or shown.
- A branch's creation in its reflog (checked 22 November 2026, git 2.56.1.windows.1): `git reflog show --date=unix --format=%gd%x09%gs refs/heads/<branch>` prints one entry a line, newest first, each selector `<branch>@{<seconds since 1970, UTC>}`. The last (oldest) line's subject is `branch: Created from <start>` for a branch made by `git branch`, `checkout -b`, `switch -c` or `worktree add -b` (asked from the main checkout too, since the reflog lives in the shared repository); a rename (`git branch -m`) moves the reflog and adds `Branch: renamed refs/heads/<old> to refs/heads/<new>` on top, the creation staying oldest; `main` after `git init` and a commit has `commit (initial): ...` as its oldest, and a clone's `clone: from <url>`.
