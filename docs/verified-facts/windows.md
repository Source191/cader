# Windows Terminal and ShellExecute: the evidence

Moved from `.claude\rules\windows.md` on 22 November 2026 (slim-claude-context) as it stood; the rule is `.claude\rules\windows.md`.

## Windows Terminal facts (verified 2026-10-24, Windows Terminal 1.25), as it stood

- [`wt.exe`](https://learn.microsoft.com/windows/terminal/command-line-arguments) focuses tabs only by index and cannot list them. Windows [UI Automation](https://learn.microsoft.com/windows/win32/winauto/entry-uiauto-win32) can: the tab items of a `WindowsTerminal.exe` window carry the tab titles as names and support [SelectionItemPattern](https://learn.microsoft.com/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomationselectionitempattern), which is how Enter switches to an open tab (`UiAutomationTabs`, through `Interop.UIAutomationClient`, a ComImport-only net35 library that builds clean under warnings-as-errors on net10.0 and, checked 14 November 2026, on net11.0 with SDK 11.0.100, and works from a pool thread; on .NET 11 it found and selected a session's open tab twice in a row with one shared client, at Windows Terminal 1.25.3131.0, 16 November 2026, 0.22.0-preview.33, for a session whose title was its name; a working session's, titled `◐ <name>` by Claude Code, was found and selected once `Domain\TabTitle.Shows` accepted one glyph and a space before the name, and an idle one's still was, 16 November 2026, 0.22.0-preview.34).
- `wt.exe` [splits its command line](https://learn.microsoft.com/windows/terminal/command-line-arguments) on every semicolon, even inside an argument passed quoted: `--title 'fix a;b'` opens a tab titled `fix a` and a second tab that fails to launch `b pwsh.exe -NoExit`. `\;` passes a literal one (`'fix a\;b'` gives the title `fix a;b`, `'a\\;b'` gives `a\;b`) and every other backslash is left as it is (`'a\b'` gives `a\b`), in `--startingDirectory` too. A double quote, which `ArgumentList` passes as `\"`, reaches the title intact (`say "hi"`); `claude --bg -n 'a;b'` keeps the name as typed (checked 2026-10-28, Windows Terminal 1.25.2733, CLI 2.1.312). So `WindowsTerminalArguments` replaces every `;` in its arguments with `\;`, and `SessionName` refuses only a blank name. With that in place the open-in-tab key (then `o`, now Enter) finds the tabs titled `fix a;b` and `say "hi"` by their exact titles, `claude attach` takes `fix a;b` by name, both titles survive the hand-off, and rename resumes under `fix c;d` (checked 2026-10-28, 0.17.0-preview.1).
- A tab shell's parent chain is `pwsh <- WindowsTerminal <- explorer` (no OpenConsole hop); `Domain\TerminalTab` walks it (any case, eight steps) for both the tab's shell and its terminal, which `TabRegistration.OwningTerminal` uses, answering a `Domain\TerminalWindow` (`Owning`, or `Any` while the tab is being claimed or its shell is outside Windows Terminal) that `FocusTabAsync` searches.
- `wt -w 0 new-tab`, which `WindowsTerminalArguments` uses, opens the tab in the most recently used window: run from a tab of a window just opened with `wt -w new`, the tab lands in that new window and not in an older one (checked 4 November 2026, Windows Terminal 1.25.2733.0, by UI Automation tab names per window). `tools\ReadmeScene` relies on it to keep the screenshot's session tabs in its own window.
- `claude attach` exits 0 after a Ctrl+Z detach, a `claude stop` and a `claude rm` from elsewhere (measured 29 October 2026, CLI 2.1.312, in a pseudo-console), so the attach tab's script ends with `if ($LASTEXITCODE -eq 0) { exit }` and the tab closes with the attach; its registration then goes stale with the shell. Stop, rename and delete close a session's live tabs through `Application\Actions\SessionTabs` (`EndCleanly` on each claimed shell, every registration forgotten), adopt ends the old tab's shell found before claude ends, and Enter reads a registration's liveness at the key. Git's "Permission denied" on `git worktree remove` is `GitException.InUse`, read only in `GitCli`. Git deletes the worktree's contents, its `.git` file and its registration before it fails on a folder a process has as its working directory, and exits 255, so nothing is left for a later remove to find (checked 13 November 2026, git 2.56.0.windows.4; `GitWorktreeRemoveShould` keeps it). `WorktreeRemover` therefore tries to delete the emptied folder for about five seconds, then finishes the removal and its branch whether or not the folder went, and the worktrees view lists any empty folder under the worktree root as empty.
- An unselected tab with a colour is that colour at alpha 77 of 255 (`deselectedTabColor.with_alpha(77)` in Windows Terminal's [`Tab.cpp`](https://github.com/microsoft/terminal/blob/v1.25.2733.0/src/cascadia/TerminalApp/Tab.cpp#L2387)) over the tab row, #2E2E2E in the default dark theme, so `Domain\TabShade.Unselected` works out each channel as `(colour × 77 + 46 × 178) / 255` and the TAB block is drawn in that shade, the console's own tab being the selected one whenever its table is read (measured 30 October 2026, Windows Terminal 1.25.2733.0: a window of one tab per palette colour captured with `PrintWindow` and `PW_RENDERFULLCONTENT`, which works with the workstation locked, each tab's fill the commonest pixel in its UI Automation box; 28 of the 33 channels exact, five one step high). A light theme or a custom tab row is not followed.
- A program sets its own tab title with OSC 2 and the tab background with OSC 4 on palette entry 264 (`ESC ] 4 ; 264 ; rgb:rr/gg/bb ESC \`); DECAC `ESC [ 2 ; 263 ; 264 , |` resets the tab's colour indices. The terminal ignores the colour for a tab launched with an explicit `--tabColor`. Claude sets the title itself while attached, and Terminal.Gui writes the top-level's `Title` as the terminal title (OSC 0) on every `Run`, so the console's `Window.Title` and `TerminalConsole` are handed one value, `ScreenContext.Title` from `Wording.TabTitle` (plain `Cader`; the version is only in the settings line), and the title and colour are written once as the console starts (`TabEscapes`; the console never hands its terminal over, so nothing retitles its tab but a dialog). Every `Runnable`, dialogs included, sets `BorderSettings.TerminalTitle` in its constructor and writes its own `Title` when it becomes modal, so every dialog calls `Tui\DialogTabTitle.Apply` with its `DialogName`: that clears the flag and writes `Wording.TabTitleDuring` (`Cader (Keys)`) on `IsModalChanged`; the main window keeps the flag and writes `Cader` back when the dialog closes.
- **What `--suppressApplicationTitle` still blocks (probed 16 November 2026, Windows Terminal 1.25.3131.0):** a throwaway tab opened with Cader's exact `wt -w new new-tab` arguments (`--profile "Cader session"`, `--title`, `--tabColor`, `--suppressApplicationTitle`, `--startingDirectory`, pwsh with an encoded command) that wrote OSC 0, OSC 1 and OSC 2 titles and set `$Host.UI.RawUI.WindowTitle` (`SetConsoleTitle`) kept its own title throughout, read by UI Automation. Yet a working session's Cader tab read `◐ <name>` at the same time (`claude-code.md`), so Claude Code's title reaches it by a route those probes did not reproduce. Repeated on 17 November 2026 (CLI 2.1.326, Windows 1.25.3131.0, UI Automation every 250 ms): a tab opened the same way and attached to a session that worked for 57 s kept its plain title throughout, although the pseudo-console capture of the same attach shows Claude writing `OSC 0;◐ <name>` and `OSC 0;◑ <name>` some thirty times, so in that run the flag blocked them and the route of 16 November is still unexplained (the workstation was apparently locked, which may matter). Claude's own output is the reliable evidence, and `claude-code.md` records what stops it writing the glyph. `UiAutomationTabs` therefore matches a tab through `Domain\TabTitle.Shows`: the name alone, or one glyph and a space before it.
- `cader setup-terminal` writes a [fragment](https://learn.microsoft.com/windows/terminal/json-fragment-extensions), `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\Cader\cader.json` (UTF-8, no BOM), that adds the "Cader" and "Cader session" profiles with [`bellStyle`, `bellSound`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-advanced) and [`icon`](https://learn.microsoft.com/windows/terminal/customize-settings/profile-general) (`logo.ico`, shipped beside the tool from `assets\icon` and copied into the fragment's own folder so a tool update cannot break the path; `--remove` deletes it with the folder; a tab not opened from these profiles keeps its own icon, and Windows Terminal has no escape sequence for one); Windows Terminal reads fragments at start-up, so a restart is needed, and a fragment cannot change `profiles.defaults`. The profile names live once in `Ports\TerminalProfiles`. While the fragment file exists, `WindowsTerminal` adds `--profile "Cader session"` to every `wt new-tab` it runs (checked on each open). What `wt` does with `--profile` for a profile it has not loaded yet is unverified (the P13 terminal checks record it).
- **Profiles Terminal hides as deleted (issue #218, observed 4 November 2026, Windows Terminal 1.25.2733.0, under the tool's earlier name, Vantage):** Terminal lists every generated profile it has loaded, fragment profiles included, in `generatedProfiles` in its `state.json`, and keeps one hidden as deleted by the user whenever its `settings.json` has no entry with that profile's `guid`, however often the fragment is rewritten. For the Store package both files are in `%LOCALAPPDATA%\Packages\Microsoft.WindowsTerminal_8wekyb3d8bbwe\LocalState`. A fragment profile's `guid` is a version 5 UUID of its name (UTF-16LE) under a namespace that is the version 5 UUID of the fragment's folder name (UTF-16LE) under Terminal's runtime namespace `{f65ddb7e-706b-4499-8a50-40313caf510a}` (`Domain\TerminalProfileId`; it reproduces the issue's observed `{58541d95-3e2c-5677-9092-a958bd152f67}` for Vantage and `{786e9622-4c30-5cd8-aa6f-cdf433f291f6}` for Vantage session). Adding the four-property entry (`guid`, `"hidden": false`, `name`, `source`) to the profile list by hand brought the profile back, and Terminal applied the saved `settings.json` with no restart. `cader setup-terminal` adds that entry, after asking (`TerminalSettings.AddProfileEntriesAsync`), and `--remove` takes it out again while it still has exactly those four properties (`RemoveProfileEntriesAsync`).
- **Computed on 13 November 2026, not yet observed in a real `state.json`:** the Cader ids, `{3d7a06d2-710f-51d9-90c9-dacae2c3ab46}` for Cader and `{cdf8708d-a821-5c97-95d0-fea560807dea}` for Cader session; and Windows PowerShell's `{61c54bbd-c2c6-5271-96e7-009a87ff44bf}`, the same hash of its name directly under `{2bde4a90-d05f-401c-9492-e40884ead1d8}`, with no source step.
- **Replacing Terminal's `settings.json` (checked 15 November 2026, Windows 11 26100, `TerminalSettingsShould.KeepTheFilesCreationTimeAndAccessRules` and the same steps in pwsh 7.7.0 on .NET 11.0.0 side by side with `File.Move`):** [`File.Replace`](https://learn.microsoft.com/dotnet/api/system.io.file.replace) of a temporary file written beside it kept the original's creation time (set to 2020), an explicit Guests read rule and its hidden attribute, and left the original's bytes under the backup name; `File.Move(..., overwrite: true)` of the same temporary file gave the file the temporary file's creation time, only the folder's inherited rules and no hidden attribute. `File.Replace` over a read-only file throws `UnauthorizedAccessException` and leaves both files as they were. So `TerminalSettings` refuses a read-only file before reading it, writes with `File.Replace` and names the backup `settings.json.<yyyy-MM-ddTHH-mm-ss>.cader.backup` in UTC.
- A running `cader.exe` locks its own files, so an upgrade fails while any Cader runs (as [`dotnet tool update`](https://learn.microsoft.com/dotnet/core/tools/dotnet-tool-update) did). `U` therefore upgrades from a tab of its own (`TabScripts.Update`: `Wait-Process` on this Cader's process id, `winget upgrade --id Source191.Cader --exact --source winget` by winget's full path, then the cader executable only when `$LASTEXITCODE` is 0) and Cader quits once the tab is open; with no winget on the PATH no tab opens and Cader stays (`WingetMissingOutcome`). The check (`UpdateCheck` over `IPackageVersions`, `WingetPackageVersions` reading winget-pkgs' version folders and the changelog at a tag) is started by `ScreenLoop` on a pool thread as the console opens (never awaited; a fault is only logged), asks at most once a day, never for a prerelease.
- [ShellExecute](https://learn.microsoft.com/windows/win32/api/shellapi/nf-shellapi-shellexecutew) (`Process.Start` with [`UseShellExecute = true`](https://learn.microsoft.com/dotnet/api/system.diagnostics.processstartinfo.useshellexecute), which cannot be given an environment) starts the associated application with the environment its caller was created with: removing variables from the live process first changes nothing (checked 2026-10-25, Windows 11 26100), and `cmd /c start` shows a blocking dialog for a missing file. `Desktop.OpenAsync` (and `StartAsync`, below) therefore makes the call from a short-lived `pwsh` child started through `IProcessRunner` (cleaned like every child), with the target as Base64 in its script (`OpenFileScript`); a file type registered under `HKCU\Software\Classes` with a handler that writes its environment to a file is the harmless way to test it.
- An editor started as a child of the console printed over its screen (#210) even with `UseShellExecute = false`, `CreateNoWindow = true` and no redirection, because a windowed program gets no console and no standard handles of its own and Electron, so VS Code, then [attaches to its parent's console](https://github.com/electron/electron/blob/main/docs/api/environment-variables.md) (`ELECTRON_NO_ATTACH_CONSOLE` turns that off). With that start, a console child (`pwsh`) got a hidden console of its own and wrote nothing to the parent's standard handles, and a windowed child (`test\Source191.Cader.NoisyEditor`) wrote nothing to them either but its `AttachConsole(ATTACH_PARENT_PROCESS)` joined the parent's console, whose process list then held the parent (checked 13 November 2026, Windows 11 26100, .NET 10, by `DesktopShould.KeepAStartedProgramsOutputOffTheConsole` against the old `StartAsync`). On .NET 11 the same start hands a windowed child the parent's standard handles instead, so the noisy editor wrote its lines into them and attached to nothing (from 10.0.15 it still attached); .NET 11's detached starts (`Process.StartAndForget`, `ProcessStartInfo.StartDetached`, or each standard handle set to `File.OpenNullHandle()`) hand it the null device, so it neither writes to the parent's handles nor attaches, because it attaches only when handed no standard output, as Chromium does (checked 14 November 2026, runtime 11.0.0, `StartAndForgetShould`). `Desktop` keeps its PowerShell child all the same (upgrade-to-net11's design, Process APIs). `Desktop.StartAsync` therefore starts the program through ShellExecute from the short-lived cleaned `pwsh` child (`StartProgramScript`, the executable and each argument as Base64), so the program's parent is that child, whose console is hidden and soon gone. In that script `catch [System.ComponentModel.Win32Exception]` catches `Process.Start`'s refusal itself, not PowerShell's wrapper, so `$_.Exception.NativeErrorCode` is set: a text file named `.exe` gives 216 and a missing file 2, with no dialog (checked 13 November 2026, pwsh 7.6 on .NET 10).
- A file whose type nothing is associated with does not make ShellExecute fail: `Process.Start` with `UseShellExecute = true` and the default `ErrorDialog = false` (which sets `SEE_MASK_FLAG_NO_UI`) on a `.cadernoapp` file returned without an exception and Windows opened its "How do you want to open this file?" picker (`OpenWith.exe`) on the desktop, so no `Win32Exception` or native error code (1155, `ERROR_NO_ASSOCIATION`, was expected) reaches the caller (checked 1 November 2026, Windows 11 26100.9711, pwsh 7.6.9 on .NET 10). Never run that start to test it again: it opens the picker. Asking first is harmless: [`AssocQueryString`](https://learn.microsoft.com/windows/win32/api/shlwapi/nf-shlwapi-assocquerystringw) with `ASSOCF_INIT_IGNOREUNKNOWN` (0x400), `ASSOCSTR_PROGID` (20) and no verb answers `0x80070483` (the HRESULT of 1155) for an unassociated extension and S_OK with a ProgID for `.cmd` (`cmdfile`), `.bat`, `.exe`, `.txt` (Notepad's AppX ProgID), `.sln`, `.slnx`, `.ps1` and `.md`; `ASSOCSTR_COMMAND` and `ASSOCSTR_EXECUTABLE` with no verb answered 0x80070483 even for associated types (they need the verb `open`), and an empty extension answers `0x80070057`. `Desktop.OpenAsync` asks it (through `FileAssociations`) for a full file path before starting the `pwsh` child and reports only that exact HRESULT as no application; URLs are never asked about.
