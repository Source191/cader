# winget: the evidence

Moved from `.claude\rules\windows.md` on 22 November 2026 (slim-claude-context) as it stood; the rule is `.claude\rules\winget.md`.

## winget facts (checked 2026-11-02 and 2026-11-03, winget 1.29.380, Windows 11 26100), as it stood

- winget's `LocalManifestFiles` setting is an admin setting, off by default (`winget settings export` lists it under `adminSettings`), and enabling it needs an administrator shell, so `winget install --manifest` of an unsubmitted manifest is the owner's step, never an unattended session's. Unprivileged symbolic links need Developer Mode (on since 3 November 2026 on the owner's machine; a session sees it without restarting); without it `ProgramFolderShould`'s link fact skips, and it always runs on CI's runners.
- **Arm Windows (13 November 2026):** GitHub's hosted `windows-11-arm` runner works for this public repository: a job on it printed `PROCESSOR_ARCHITECTURE=ARM64` (image `windows-11-vs2026-arm64` 20261101.203.1, Windows 11 10.0.26200, pwsh 7). That image has no `winget` on the PATH. The three dependencies each have an `arm64` installer, read from the winget-pkgs manifests with `gh api` because no Arm machine was at hand (`winget show` reads the same manifests): `Microsoft.WindowsTerminal` 1.25.3131.0 (msix, released 2026-11-11), `Microsoft.PowerShell` 7.7.0.0 (msix, 2026-11-10) and `Git.Git` 2.56.0.4 (inno, user and machine scopes, 2026-10-26). Re-run `winget show` on an Arm machine when installing there (task 5.1). `Compress-WingetBuild.ps1` reads the PE machine field of `libonigwrap.dll` (0x8664 x64, 0xAA64 Arm64).
- `wingetcreate` 1.12.13.0 (`microsoft/winget-create`, released 23 July 2026) is what `publish.yml` pins, with its SHA-256; `update <id> --version --urls '<url>|x64' --submit --token` updates an existing manifest and opens the pull request, and fills `ReleaseNotesUrl` and `ReleaseDate` from a GitHub release (its `doc/update.md` at that tag).
- **The install spike (3 November 2026, winget 1.29.380, Developer Mode on, local manifests of this repository's zip and of a single-file probe built the same way, from a throwaway prerelease):** a portable zip is extracted whole into a folder of its own, `%LOCALAPPDATA%\Microsoft\WinGet\Packages\<id>_<source>` (`Source191.Cader__DefaultSource` for a local manifest; the community source's name was not seen), so `libonigwrap.dll`, `CHANGELOG.md`, `logo.ico` and `THIRD-PARTY-NOTICES.txt` sit beside `cader.exe`, and the alias is a symbolic link `%LOCALAPPDATA%\Microsoft\WinGet\Links\cader.exe` to it, that folder already on the user PATH. Started through the link, .NET 10 answers the **link's** folder for both `Environment.ProcessPath` and `AppContext.BaseDirectory` (`...\WinGet\Links\`), where none of the other files are, so the program reads its own files through `ProgramFolder.Of`, which follows the link with `File.ResolveLinkTarget(..., returnFinalTarget: true)` to the package folder. `cader --version` through the link printed the csproj version. `PackageDependencies` were listed and skipped as already installed.
- `winget upgrade` keeps the same package folder and link. With the program running, it fails with exit `0x8A150052` and "remove: Access is denied" on the executable, **after** deleting the package's other files, so the old executable keeps running but its folder has lost `CHANGELOG.md`, `logo.ico` and the native library until an upgrade with nothing running succeeds (it did, and restored them). `U` avoids it by waiting for Cader to exit; the README says to upgrade with no Cader open.
- A local-manifest install is listed as `ARP\User\X64\<id>__DefaultSource`, so `winget uninstall --id Source191.Cader --exact` finds nothing (`0x8A150014`) and the ARP id must be given; uninstalling removes the link and the package folder and leaves `%LOCALAPPDATA%\Cader` alone. A dotnet tool's shim in `~\.dotnet\tools` comes before the Links folder on the PATH, so it shadows the winget `cader` until it is uninstalled. Not checked: the PATH fallback winget uses without Developer Mode.
- **The first manifest's install (13 November 2026, winget 1.29.380 and wingetcreate 1.28.1.0, local manifest of v0.21.0 without `ArchiveBinariesDependOnPath`):** `winget install --manifest` listed the three package dependencies, verified the zip's SHA-256, extracted it, added the alias `cader` and printed the installation notes; the package folder held exactly `cader.exe`, `CHANGELOG.md`, `libonigwrap.dll`, `logo.ico` and `THIRD-PARTY-NOTICES.txt`, `cader --version` printed 0.21.0 and the console listed its sessions, so the package folder need not be on the PATH. `winget uninstall --id "ARP\User\X64\Source191.Cader__DefaultSource"` removed it, with a harmless "Failed when searching source: msstore" warning. `winget validate` warns that icons need a verified publisher and passes without them. wingetcreate's Tags prompt does not split on commas, its dependency item asks only for MinimumVersion, and it saves the manifests under `~\source\repos\manifests` before asking to submit.
