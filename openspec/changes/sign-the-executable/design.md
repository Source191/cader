# Design

## Context

0.21.0's release job "checks nothing out and runs no build" and holds only the rights to attest and publish (`pipeline.yml`). The `check` job is a matrix since `add-win-arm64-build`: a `win-x64` leg on `windows-latest` and a `win-arm64` leg on `windows-11-arm`, each building, zipping (`Compress-WingetBuild.ps1`: exactly `cader.exe`, `libonigwrap.dll`, `CHANGELOG.md`, `logo.ico`, `THIRD-PARTY-NOTICES.txt`) and smoke-checking its own zip, and on a release uploading it as `release-<rid>`; the release job needs both legs, attests both zips and publishes them together. Signing needs a credential, so it must not go into either job as it stands. winget records the SHA-256 of each zip, so each `cader.exe` must be signed before the zip that is hashed and attested is made.

Cader is the owner's personal project, owned by the owner (MAINTAINING.md, Ownership). The signing account is the project's own, set up and held by the owner.

## What was verified (14 November 2026)

- **Eligibility** ([signpath.org/terms](https://signpath.org/terms), marked as a draft): an OSI-approved licence with no commercial dual licensing for every component (Cader is Apache-2.0, `gh api repos/Source191/cader` answers `public Apache-2.0`); no malware or proprietary component; actively maintained; "already be released in the form that should be signed" (it is: zips on GitHub Releases and winget); functionality described on the download page; "The team must only sign software artifacts built from their own source code", but unsigned upstream binaries such as `libonigwrap.dll` may be included; uninstallation provided where there is installation (winget uninstall).
- **Team and MFA:** "All team members must use multi-factor authentication" for SignPath and the repository; roles are authors, reviewers (every change by a non-committer is reviewed, which the "Owner approves main" ruleset already enforces) and approvers. Whether a sole maintainer may hold all three is not stated: the application says so plainly.
- **Code signing policy page:** "A code signing policy must be specified on the project's home page", with "Code signing policy" as a header or link on the home and download or release pages, the line "Free code signing provided by SignPath.io, certificate by SignPath Foundation", the team roles and members, and a privacy policy or the default statement ("This program will not transfer any information to other networked systems unless specifically requested by the user or the person installing or operating it").
- **Metadata:** "All signed binaries must have metadata attributes set and enforced": the product name is the project's name and the product version is the same in every file of a build. `src\Source191.Cader\Source191.Cader.csproj` sets `Version`, `Authors` and `Copyright` but no `Product`, so the SDK's default (the assembly name) applies; task 2.1 checks the PE version resource and sets `Product` to `Cader` if needed.
- **Manual approval:** "Every release needs manual approval for signing." A signing policy with the approval process enabled emails each approver for each request, and one denial aborts it ([docs.signpath.io/projects](https://docs.signpath.io/projects)). This is SignPath's rule for the Foundation's certificate and cannot be configured away.
- **Publisher:** "The code signing certificate is issued to SignPath Foundation." A signed `cader.exe` shows SignPath Foundation as its publisher in Properties, Digital Signatures and in `Get-AuthenticodeSignature`; the owner's name and the project's name appear nowhere in the certificate. That is the price of a free certificate, and the README says so.
- **The action** ([docs.signpath.io/trusted-build-systems/github](https://docs.signpath.io/trusted-build-systems/github), [action.yml](https://github.com/SignPath/github-action-submit-signing-request)): `signpath/github-action-submit-signing-request`, tag `v3.0` at commit `f6d04783b4569d051e0c80105fe66e82819d0092`, committed 10 September 2026 (a tag; the repository has no GitHub Releases). It takes a mandatory `api-token` ("the API token for a user with submitter permissions"), `organization-id`, `project-slug`, `signing-policy-slug`, optional `artifact-configuration-slug`, and one `github-artifact-id` from a preceding `actions/upload-artifact` step; it waits (`wait-for-completion`, default true, `wait-for-completion-timeout-in-seconds` default 600) and downloads the signed result to `output-artifact-directory`. Its `github-token` needs `actions: read` and `contents: read`.
- **Origin checks:** the artefact must be a workflow artefact of the run that submits it; "for OSS projects, all jobs leading up to the signing request must run on GitHub-hosted agents" (`windows-latest` and `windows-11-arm` are); the SignPath GitHub App reads the run; a signing policy's "Allowed branch names" ([docs.signpath.io/origin-verification](https://docs.signpath.io/origin-verification)) limits it to `main`; `github-build-policies` offers `disallow_reruns`.
- **The credential:** CI users "can only authenticate with an API token", and SignPath recommends storing it "in your CI system's build settings as secret values" ([docs.signpath.io/users](https://docs.signpath.io/users/)). There is no OIDC route, so the token is a stored secret.
- **Approval time:** not published; the apply form ([signpath.org/apply](https://signpath.org/apply)) did not render for a fetch, and one third-party guide ([Trial Submission Studio](https://rubentalstra.github.io/Trial-Submission-Studio/development/windows-signing.html)) says "typically a few days". Treat it as unverified.
- **Not verified:** whether a Foundation project sets its own allowed branches, approvers and artefact configuration or SignPath sets them; whether one artefact configuration may sign two PE files at different paths in one zip (the docs say a configuration can sign several files in one archive but give no such example). Task 1.2 proves both.

## Decisions

- **Signing service: SignPath Foundation.** Free for an OSI-licensed open-source project, which Cader is, and the owner prefers no monthly cost. The certificate and its private key stay with SignPath, so nothing is stored or renewed here. Rejected: **Azure Artifact Signing** (about US$10 a month, an Azure subscription and identity validation, which the owner prefers to avoid) and a purchased OV or EV certificate (an annual cost and a private key to protect).
- **One signing request per release, signing both executables.** A request takes one artefact, and SignPath's per-release approval makes each request a click, so one request carries both: the `sign` job downloads both `release-<rid>` artefacts, extracts each `cader.exe`, and uploads one artefact holding `win-x64\cader.exe` and `win-arm64\cader.exe`, which an artefact configuration with a `<zip-file>` root signs as two PE files, restricted to product name `Cader` and the release's product version. Only Cader's executables are signed; `libonigwrap.dll` is third party and the terms allow it unsigned.
- **A `sign` job with only signing steps,** between `check` and the new `signed` job, running only on a push to main that changes `Version`, in the `signing` environment, on `windows-latest`, with `contents: read` and `actions: read` and nothing else: it downloads, extracts, uploads the unsigned pair, calls the SignPath action (pinned by commit) and uploads the signed pair as `signed-executables`. It checks out nothing and runs no build, no installer and no test, so the token's reach is that one step.
- **A `signed` job per architecture,** a matrix on the same two runners as `check`, with no environment and no secret: it checks out the repository, downloads its architecture's `release-<rid>` zip and the signed pair, puts the signed `cader.exe` in place of the unsigned one, rezips with `Compress-WingetBuild.ps1` (same five files, same name), runs `Test-Signature.ps1`, the version check and the smoke check on the signed zip, and uploads it as `signed-<rid>` (the x64 leg with the release notes). The smoke steps move into a composite action `.github\actions\smoke-check` that `check` and `signed` share, so the two smoke checks cannot drift. The smoke check needs the Claude Code installer (`irm | iex`) and a build of `tools\HeadlessTerminal`, which is why it is not in the `sign` job.
- **The release job** needs `signed`, reads `signed-*` instead of `release-*`, and attests and publishes exactly the zips that were signed and smoke-checked; nothing else in it changes.
- **The `signing` environment** accepts only `main`, has no required reviewer, and holds the one secret `SIGNPATH_API_TOKEN` as an environment secret (never a repository secret) and the organisation id and the project, signing policy and artefact configuration slugs as environment variables. No GitHub reviewer, because SignPath already asks for an approval and two clicks per release would be one too many.
- **The token belongs to a SignPath CI user** with only the submitter role on the release signing policy, so it can submit but never approve; the approver is the owner's interactive account, with MFA.
- **Three locks on signing from main:** the `signing` environment hands the token only to a run on `main`; the signing policy's allowed branch is `main` and SignPath checks the origin from GitHub, not from the run; and every request waits for the owner's approval. A pull request, a fork or a copy of the workflow on another branch never reaches the token.
- **Waiting for approval:** the action waits up to 60 minutes (`wait-for-completion-timeout-in-seconds: 3600`, job `timeout-minutes: 70`) for the owner to approve the request SignPath emails about. A denial, an expiry or a SignPath outage fails the `sign` job, so no release is published, and a rerun of the failed jobs makes a new request (so `disallow_reruns` stays off). The GitHub Release therefore follows the merge by however long the approval takes, not half a minute.
- **One verifier:** `Test-Signature.ps1` wraps `Get-AuthenticodeSignature`: status `Valid`, a timestamp, and the signer certificate's subject naming SignPath Foundation (the expected subject is a parameter, read from the first real signature in task 1.2). The `signed` job runs it on each signed `cader.exe`, and `publish.yml` runs it on each downloaded zip's executable, naming the architecture when one fails, so the two checks cannot drift.
- **Prereleases are signed:** the same jobs, so the thing tried is the thing shipped and the signing path is exercised on every release. The cost is one SignPath approval per prerelease, Dependabot bumps included.
- **The code signing policy page:** a "Code signing policy" section in the README with the attribution line, the team (the owner, as author, reviewer and approver), and a link to the README's Privacy line rather than the default statement, which the daily update check makes untrue; the stable release notes carry a "Code signing policy" link. MAINTAINING says how signing is set up and what to do when a request waits, is denied or the token lapses.
- **Alternative: a matrix `sign` job, signing each architecture on its own runner:** simpler wiring, but two requests and two approvals per release. Rejected.
- **Alternative: sign in the check job on main:** puts the token in the job that runs the tests, the installer and third-party build steps. Rejected.

## Risks and open questions

- **[Approval and acceptance]** SignPath Foundation accepts projects at its discretion ("no independent arbitration") and may pause a subscription or revoke the certificate; approval of the application is unverified in length (a third-party "few days"). Nothing starts until it is accepted (task 1.1).
- **[Privacy rule]** the terms require software that "collects user data and transfers it to systems not specified by the user" to show its privacy policy during installation and offer an installation option to turn the transfer off. Cader's anonymous daily update check sends no user data and is turned off on the Config tab, not at install; the application describes it, and if SignPath asks for more, the change is re-planned rather than the check hidden.
- **[A sole maintainer]** the terms describe a team of authors, reviewers and approvers trusted by the whole team; Cader has one maintainer holding all three. The application says so; if SignPath refuses it, Azure Artifact Signing is the fallback and this design is revisited.
- **[Every release waits for a click]** a merge is no longer a release on its own: the owner must approve in SignPath within the hour, or rerun the failed jobs later. Accepted, as the Foundation's condition for a free certificate.
- **[Publisher name]** users see SignPath Foundation, not Cader or the owner, as the publisher. The README says so and how to check the signature.
- **[SmartScreen reputation]** reputation attaches to the certificate; the Foundation's is shared with other projects, which may help or hurt. The integration check records what a clean machine shows rather than promising no warning.
- **[A stored secret]** the token is a stored secret, unlike the OIDC route Azure would have given; it is limited to an environment that accepts only `main`, belongs to a submit-only CI user, and cannot sign without the owner's approval. Rotation is in MAINTAINING.
- **[winget hash]** nothing already in winget-pkgs changes: signing applies only to new versions, whose hash is of the signed zip.
- **[Signature breaks on rezip]** a zip does not alter the executable's bytes, but `Test-Signature.ps1` and the smoke check on the signed zip prove it.
- **[Service outage]** a SignPath outage blocks a release; accepted, since an unsigned release is what this change exists to prevent, and a rerun after the outage is cheap.
